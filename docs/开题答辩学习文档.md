## 1. 一页总览：30 秒讲清这个项目

**一句话定位**：一个**本地部署、事实可溯源、支持自然语言局部迭代**的多智能体协同文旅行程规划平台。

**完整闭环**：

```
输入参数 → 智能体协同生成攻略 → 自然语言修改优化 → 路线榜单推荐（沉淀/复用）
```

**宣传语式的概括（开题报告原文口径）**：

> 一个平台、七类智能体、五个核心机制、两套评估体系。
>
> - **一个平台**：Vue3 前端 + Java 业务后端 + Python Agent 服务三端协同
> - **七类智能体**：总控调度、路线规划、气象服务、景点资讯、餐饮住宿、预约规则、交互修正
> - **五个核心机制**：事实来源溯源与时效治理、确定性算法动线优化、中心化 DAG 编排与任务状态机、局部修改与不可变版本、虚拟积分账务守恒
> - **两套评估体系**：机器指标（通过率/来源完整率/保真率/时延/成本）+ 人工评分（合理性/可用性/攻略味）

**核心技术路线（背下来，答辩反复用）**：

> **事实靠数据、计算靠算法、理解与表达靠模型；契约先行、编排中心化、版本不可变、降级透明化。**

**六个可验收子目标**：

| # | 子目标 | 量化验收线 |
|---|---|---|
| G1 | 结构化行程生成 | 硬约束满足率 100%，事实字段来源完整率 100% |
| G2 | 多智能体协同 | 7 类 Agent 按固定 DAG 协作；10 并发 P95 ≤ 180 秒，10 秒内首进度 |
| G3 | 自然语言迭代 | 局部修改 P95 ≤ 60 秒，未影响区块保真率 100% |
| G4 | 榜单与 UGC | 一键复用、内容治理 |
| G5 | 历史与偏好分析 | 画像反哺生成 |
| G6 | 评估体系 | ≥30 案例，机器指标 + 人工评分双轨 |

## 2. 背景与意义：为什么要做

### 2.1 三类痛点（立论依据）

| 现有方式 | 痛点 |
|---|---|
| 传统攻略获取（内容平台搜索、旅行社定制） | 信息碎片化、时效性差、与个人需求错配；用户在地图/天气/内容/票务多个 App 之间反复横跳、手工拼装 |
| 通用大模型直问（“帮我规划三天行程”） | 幻觉严重（编造时长/票价/预约政策）、信息过期、缺实时数据、无法结构化迭代修改 |
| 商业行程规划 SaaS | 定制深度有限；修改是“推倒重来”式全量重生成；数据不自持、成本不可控 |

### 2.2 本项目的三方面意义

1. **工程上**：交付可运行、可部署、可演示的三端系统，为自由行深度用户提供信息聚合、深度定制、可迭代、可沉淀的规划工具。
2. **研究上**：验证“事实/表达分离”的反幻觉架构在行程规划场景的可实施性，沉淀一套可评估、可复现的多智能体协同规划方法。
3. **范式上**：通过来源快照、时效治理、不可变版本、积分账务守恒，为“可控、可回放、可审计”的大模型应用落地提供工程范式。

### 2.3 与参考项目 TripStar 的关系（必考题）

TripStar（旅途星辰，GPL-2.0，FastAPI+Vue3+多 Agent）是同定位开源项目，已验证「异步任务+进度推送、三路并行采集、LLM 输出容错、双地图回退」等关键组合。**我们自研为主体、TripStar 只作效果对照基线**（规避 GPL-2.0 对外分发传染性）。

TripStar 的五大缺口 = 我们的增量价值：

| # | TripStar 缺口 | 本项目对应能力 |
|---|---|---|
| 1 | 迭代闭环缺失（只能问不能改、无版本/多方案） | G3 自然语言局部修改 + 不可变版本链（创新点二） |
| 2 | 无沉淀层（无用户体系/榜单/UGC） | G4 榜单社区 + UGC 飞轮（创新点六） |
| 3 | 规划智能靠 LLM 硬扛（路线/时长全出自 LLM） | 事实/表达分离 + TSP 算法动线（创新点一、三） |
| 4 | 预约信息不成体系（游记提纯、时效不可控） | 人工核验规则库 + 30 天 stale 治理 |
| 5 | 无导出/提醒/缓存策略 | PDF/ICS/长图、站内提醒、多级缓存 |

**明确不做（Out of Scope，答辩被问“边界”时用）**：机酒预订支付闭环、原生 App/小程序、多人实时共编、行中实时伴游、境外目的地、内容平台爬取（彻底不接，合规考量）。

**行程单元长什么样**（G1 输出维度）：时间节点（半小时粒度）→ 地点（含坐标）→ 游览时长 → 交通方式/路线/通勤 → 当日天气提示与备选 → 餐饮候选 → 预约提示（渠道/放票/票价）→ 玩法避坑 → 住宿建议 → 预算明细面板（门票/餐饮/住宿/交通分维度）。

## 4. 总体设计：六层架构与三端分工

### 4.1 分层架构（对应开题报告“图1 分层架构图”）

```
前端交互层   Vue3 + Vite + TS + Pinia + Element Plus（高德 JS SDK 预留）
     │  REST 命令 / SSE 进度
业务服务层   Java 21 / Spring Boot 3 —— 业务数据唯一写入方
     │  事务 Outbox → Redis Streams（Consumer Group）
智能体编排层 Python FastAPI + LangGraph —— 总控 + 6 专业 Agent
     │  经适配器
第三方适配层 高德 Web 服务 / 和风天气 / OpenAI 兼容 LLM（限流、缓存、降级、多源切换、Mock）
数据存储层   MySQL 8（业务事实）/ Redis（队列/缓存/限流）/ Chroma（知识向量）/ 受控对象目录
大模型层     配置化 LLM 网关（按任务路由、Schema 校验、JSON 容错、调用留痕）
```

### 4.2 三条铁律（架构原则，来自 [总体架构设计.md](docs/architecture/总体架构设计.md)）

1. **Java 是 MySQL 唯一业务写方**；Python Agent 服务只经 REST/OpenAPI 读任务、回写步骤结果，不直连业务库。
2. **MySQL 保存业务事实**；Redis Streams 只负责投递，Redis Cache、Chroma、对象文件都不能替代业务事实。
3. **命令走 REST，进度走 SSE**；所有重试、回放、结算必须幂等。

### 4.3 为什么双栈（Java + Python）？

| 问题 | 答案 |
|---|---|
| 为什么不全 Java？ | LangGraph / LLM 生态是 Python 原生，Agent 编排与算法层留在 Python 效率最高 |
| 为什么不全 Python？ | 团队 Java 储备更强，业务侧（用户/行程/版本/积分/社区）用 Spring Boot 质量更有保障 |
| 双栈代价怎么管？ | REST/OpenAPI 契约 M0 冻结（[contracts/openapi/](contracts/openapi/)），服务边界从架构上隔离数据一致性风险（创新点四） |

### 4.4 异步任务与进度（设计已冻结）

- `planning_task` 表是任务**事实来源**（含 `idempotency_key` 唯一键、`state_version` 乐观锁）。
- **事务 Outbox**（[ADR-0002](docs/architecture/ADR/0002-transactional-outbox-redis-streams.md)）：任务创建 + 积分预扣 + Outbox 写入在**同一 MySQL 事务**提交 → Outbox Relay 至少一次发布到 **Redis Streams Consumer Group** → Python Worker 消费（租约/心跳/attempt_no/业务幂等）。
- 进度走 **SSE**：`task_event` 仅追加、`sequence_no` 单调，断线从最后序号补拉去重。
- 为什么这样设计：解决“扣费未执行/执行未记账”的分布式一致性问题；MySQL 是事实源，Redis 只传递、可重建。

### 4.5 任务状态机（15 态）

来自 [任务状态机.md](docs/architecture/任务状态机.md) 与 `planning_task.status`：

```
CREATED → BALANCE_RESERVED → QUEUED → PARSING → COLLECTING → SCHEDULING
   → ROUTING → ASSEMBLING → AWAITING_CONFIRMATION
   → SUCCEEDED / PARTIAL / FAILED / CANCELLED → REFUNDED
```

关键设计：乐观锁 CAS 状态转移（条件 UPDATE + 影响行数检查）、各阶段时限（PARSING 30s、COLLECTING 60s、确认等待 24h、首次生成全局 180s/局部修改 60s Deadline）、事件仅追加可回放。

### 4.6 数据模型（39 张表，S04 冻结）

一次性迁移 [V1__initial_s04_schema.sql](backend/src/main/resources/db/migration/V1__initial_s04_schema.sql)（Flyway，只增不改），主键统一 `BINARY(16)` UUID。按域分组：

| 域 | 表 | 设计要点 |
|---|---|---|
| 账号 | `user_account`、`user_session` | 登录失败锁定、refresh 只存 SHA-256 摘要 |
| 行程/版本 | `trip`、`trip_city`、`city`、`trip_version`、`plan_snapshot`、`change_set` | **不可变版本**：`version_no` + `etag` + `content_hash` + `parent_version_id` 版本链；`change_set` 含 ROLLBACK 类型 |
| 来源溯源 | `source_record`、`source_snapshot`、`trip_version_source` | 字�级溯源 `field_path`；新鲜度 FRESH/STALE/UNKNOWN |
| 任务/编排 | `planning_task`、`task_step`、`task_event`、`outbox_event`、`agent_result` | 租约 `lease_owner/lease_expires_at`、`sequence_no` 事件流、死信 `dead_at` |
| POI/知识/规则 | `poi`、`poi_snapshot`、`poi_alias`、`knowledge_entry`、`knowledge_chunk`、`reservation_rule` | POI 稳定身份 + 别名消歧；知识分块含向量引用 |
| 积分 | `points_account`、`points_quote`、`points_ledger` | 流水**仅追加**；CHECK 强制 `balance_after = balance_before + delta` |
| 社区/偏好 | `post`、`post_comment`、`interaction`、`moderation_case`、`report`、`ranking_entry`、`user_preference`、`preference_evidence`、`preference_summary` | 敏感词过滤 + 人工抽审 + 举报下架 |
| 其他 | `object_metadata`、`export_job`、`reminder_candidate`、`notification`、`audit_event` | `dedupe_key` 幯等；审计全程留痕 |

详细字典见 [数据设计说明书](docs/多智能体协作文旅规划平台-数据设计说明书.md)，ER 图见 [docs/diagrams/](docs/diagrams/)。

## 5. 多智能体设计：七类 Agent 与协作 DAG

### 5.1 划分原则（五条划分线，[03-多智能体规范](docs/03-多智能体系统规范.md)）

1. **对外/对内**：只有总控对外，其余 6 个对内、不互相直连。
2. **事实数据**：每个 Agent 只从自己指定的数据源取数，**不跨源**。
3. **能不能编**：所有 Agent **都不能编造事实**，查不到就说查不到。
4. **失败降级**：每个 Agent 都有明确降级策略，**单个降级不阻塞整体**。
5. **修改范围**：交互修正只做最小改动，**不全量重生成**。

### 5.2 七类 Agent 一览

| 编号 | Agent | 对外/内 | 数据源 | 输出 | 契约目录 |
|---|---|---|---|---|---|
| 01 | 总控调度 Orchestrator | **对外** | 子 Agent 结果 | 最终行程 plan | [agents/01-orchestrator/](agents/01-orchestrator/) |
| 02 | 路线规划 | 对内 | 地图 API | 排序点位序列、逐段路线 | [agents/02-route-planner/](agents/02-route-planner/) |
| 03 | 气象服务 | 对内 | 天气 API | 逐日天气、出行建议、备选 | [agents/03-weather/](agents/03-weather/) |
| 04 | 景点资讯 | 对内 | 本地知识库 | 景点资讯卡 | [agents/04-attractions/](agents/04-attractions/) |
| 05 | 餐饮住宿 | 对内 | POI 检索 | 每餐候选、住宿建议 | [agents/05-dining-lodging/](agents/05-dining-lodging/) |
| 06 | 预约规则 | 对内 | 人工规则库 | 预约卡、预约时间线 | [agents/06-reservation-rules/](agents/06-reservation-rules/) |
| 07 | 交互修正 | 对内 | 当前行程+知识库 | 影响范围、最小改动、变更摘要 | [agents/07-revision/](agents/07-revision/) |

每个 Agent 目录固定三件套：`input.schema.json` / `output.schema.json`（JSON Schema Draft-07）+ `prompt.txt`。**Schema 即团队接口协议**，是 8 人并行开发的对齐基础（创新点四）。

### 5.3 公共消息封套（Envelope）

所有 Agent 输出顶层必须携带：`schema_version`、`task_id`、`trace_id`、`request_id`、`generated_at`、`status`，以及条件必填的 `message`、`error_code`、`degraded_fields`。

| status | 含义 | 要求 |
|---|---|---|
| `ok` | 完整成功 | — |
| `partial` | 部分子项缺失 | `degraded_fields` 非空 |
| `degraded` | 触发降级 | `degraded_fields` 非空 |
| `failed` | 失败 | `error_code` + `message` 必填，**不得被迫生成成功载荷** |

每条事实还必须携带 `source_metadata`（来源、取得时间、有效期、新鲜度、是否估算）。四态示例在 [contracts/examples/](contracts/examples/)（7 个 Agent × ok/partial/degraded/failed 共 28 个样例）。

### 5.4 首次生成 DAG（对应开题报告“图2”）

```
[0] 鉴权 + 服务端报价 + 积分预扣
[1] 创建 planning_task + Outbox
[2] 需求解析（自由文本→结构化偏好）+ 可行性预检（PARSING）
[3] ── 并行采集（COLLECTING）──  景点资讯 ∥ 天气 ∥ 预约规则
[4] 日级分配（SCHEDULING）：哪天去哪几个点
[5] ── 逐日路线并行（ROUTING）──  第 1 日路线 ∥ 第 N 日路线
[6] 餐饮住宿注入（沿确定动线）
[7] 确定性质量校验（ASSEMBLING）
      ├─ 硬冲突 → AWAITING_CONFIRMATION（携选项问用户）
      └─ 可交付 → 整合与来源快照
[8] Java 原子创建不可变 trip_version → SUCCEEDED / PARTIAL（确认预扣）
        不可恢复失败 → FAILED / REFUNDED（全额退款）
```

**多方案模式**：步骤 [4] 分叉 2~3 个编排策略，[5][6] 各自执行，[3] 的采集数据全程共享（成本不翻倍）。

## 6. 五个核心机制（项目的“骨架”）

### 机制一：事实来源溯源与时效治理（创新点一、五）

- 事实字段（时长/票价/预约政策/开放时间/天气）**只来自**地图 API、天气 API、人工规则库、已发布知识库。
- 每条事实附**来源快照**：来源、取得时间、有效期、`data_type`、`is_estimated`，随行程输出。
- 规则超过 30 天未核验 → `stale`，过期数据**不能作为确定性硬约束**，必须对用户显式标注“请以官方渠道为准”。
- 无来源、过期、冲突、估算、失败**必须显式呈现**；LLM 只做理解与表达，**不得补写事实**（未覆盖景点返回未知，不用“LLM 通识”填补）。
- 前端对应：S07 演示页每个行程节点带 `EvidenceBadges`（Mock/示例/估算/待核验徽章）——见 [EvidenceBadges.vue](frontend/src/components/s07/EvidenceBadges.vue)。

### 机制二：确定性算法动线优化（创新点三）

顺序优化本质是**带时间窗的 TSP 类问题（TSPTW）**，由算法求解（贪心 + 2-opt），LLM 只把柔性偏好（“日落时分要在江边”）翻译为时间窗约束。详见第 7 章 ALG-05。

### 机制三：中心化 DAG 编排与任务状态机（创新点三）

- **中心化编排（Orchestrator-Worker）**：总控持有全局状态，子 Agent 无状态、不互相通信。理由：链路可控、可调试、可回放，优于去中心化自由协作的延迟与不确定性。
- 15 态任务状态机 + 事务 Outbox + Redis Streams 至少一次投递 + 业务幂等。详见 4.4/4.5。

### 机制四：局部修改与不可变版本（创新点二）

- 意图三分类：`query`（只读回答，不建版本不扣费）/ `change`（走修改链路）/ `ambiguous`（返回澄清问题）。
- **影响白名单**：`affected_days` / `affected_agents` / `locked_paths`；只重跑白名单内 Agent，**未影响区块 100% 保真**（`before_hash == after_hash` 可验证）。
- **已发布版本不可原地修改**；回滚 = 以历史版本为内容来源**创建新版本**；版本上限 10 个/行程。
- **ETag 乐观锁**：并发修改旧 ETag 返回 409，不覆盖。
- 波及必去景点/锁定项/已确认预约 → 先向用户确认（ALG-03），确认前不写版本。

### 机制五：虚拟积分账务守恒（创新点六）

- 虚拟积分，**不可提现、不对应法定货币**，不接真实支付（合规红线）。
- 定价：新用户赠 100；1/2/3 套方案预扣 10/18/25；已确认局部重规划 2 分；问答/澄清/失败/执行前取消免费。
- 生命周期：`quote → reserve → confirm → refund`；流水**仅追加**；`business_reference` 唯一幂等键；确认与退款互斥；失败全额退款。详见 7 章 ALG-13。

## 7. 算法设计：评委最可能深挖的部分

全部 15 个算法（ALG-01 ~ ALG-15）定义在 [算法设计说明书](docs/多智能体协作文旅规划平台-算法设计说明书.md)。答辩重点讲下面 6 个。

### 7.1 ALG-05 逐日路线排序（贪心 + 2-opt）—— 项目最硬的算法

**问题建模**：单日给定点位集合 + 固定起终点 + 时间窗 + 必去约束，求游览顺序与逐段路线 = **TSPTW（带时间窗旅行商变体）**。

**求解步骤**（伪代码见说明书 4.5）：

```
1. build_travel_matrix     O(n²) 构建点对通勤矩阵（精确缓存优先，ALG-06）
2. greedy_construct        O(n²) 可解释的贪心构造初始顺序（固定 seed）
3. 2-opt 局部搜索          反复交换边对，成本下降且 feasible 则接受，直到收敛
4. feasible(order) 校验    闭馆/午休/时间窗/固定起终点/必去点/零负时长/时区边界
5. compute_segments        逐段路线；断言 总通勤 == 逐段汇总
```

**为什么不用 LLM 排顺序**（高频问题）：LLM 幻觉会产出“上午颐和园下午天坛再回香山”式反人类动线；TSPTW 是确定性组合优化问题，算法给出**稳定、可解释、可复现**的解（相同输入输出逐字一致，固定 seed + 算法版本）。

**硬约束**：通勤/游玩/排队/用餐时间**分离计算**，不得混入路线时长；直线估算必须标 `is_estimated=true` 且**不通过“行程可行”硬 Gate**。

**三级降级**：精确缓存 → 直线估算（显式标注）→ 无解则 `failed`（不输出伪路线）。

**复杂度**：矩阵 O(n²) 查询（可缓存）+ 贪心 O(n²) + 2-opt 多轮至收敛。

### 7.2 ALG-02 冲突消解与优先级裁决

**六级硬约束优先级**（高优先级不得被低优先级绕过）：

1. 用户显式硬约束（城市/日期/必去点/固定起终点/锁定项/已确认选择）
2. 闭馆、预约、生效期、开放时间
3. 可达性、交通方式、时间窗
4. 天气安全与明确风险
5. 预算硬上限
6. 软偏好（节奏/主题/口味/评分）

**确定性四步自动消解**（顺序冻结，每步都重新校验开放时间/可达/预算/来源）：

```
同日换序 → 同城同类候选替换 → 跨日互换 → 删除最低优先级软偏好项
```

四步都失败 → 若波及保护项转 `AWAITING_CONFIRMATION`（携选项问用户）→ 否则 `FAILED`。**不得删除必去/锁定项、不得用过期事实作硬约束、不得用自然语言掩盖结构化冲突。**

### 7.3 ALG-10 修正意图分类与最小影响范围

```
revise(base_version_id, current_plan, locked_paths, request):
  intent = classify(request)                  # query / change / ambiguous
  query     → 只读回答（不建版本、不扣费、不触发子 Agent）
  ambiguous → 返回澄清问题
  change    → locate_impact() 得到 affected_days / affected_agents / locked_paths
              atomic_changes()  # add / remove / replace / reorder
              波及保护项或范围不确定 → 先确认（ALG-03）
              否则 → 只调度白名单 Agent、复用未影响区块 → 原子创建子版本 + change_set
```

**验收核心指标**：未影响区块保真率 100%（JSON Patch/领域 diff 验证 `before_hash == after_hash`）；旧 ETag → 409；确认被拒/超时 → 原版本不变。

### 7.4 ALG-13 积分计价、预扣、确认与退款

```
create_quote: 1/2/3 套 → 10/18/25 分（服务端定价，不信任前端）
reserve:  同事务 = 锁账户行(FOR UPDATE) → 幡等键 reserve:{task} 查流水唯一键
          → 插入 RESERVE 负向流水 + 更新余额 + 任务 CREATED→BALANCE_RESERVED(CAS)
          + 写 Outbox
settle:   SUCCEEDED → CONFIRM(delta=0)；PARTIAL 有可用版本 → CONFIRM，否则 refund
          FAILED/CANCELLED → refund
refund:   幡等键 refund:{task}，全额退回；与 confirm 互斥（同一 hash 互查）
```

**守恒不变量（SQL CHECK 强制）**：`balance_after = balance_before + points_delta`；余额非负；RESERVE 必为负、GRANT/REFUND 必为正、CONFIRM 必为 0；`business_reference` 全局唯一 = 天然幂等键。**每个业务引用最多产生一次经济效果**，重复请求返回原结果（`reused=true`），重复消息/崩溃恢复零重复扣退。

### 7.5 ALG-07 天气预报窗口与气候统计分流（“降级透明”的典型）

- 预报窗口**内** → `forecast`（逐日/逐时段预报）。
- 预报窗口**外**（通常 7~15 天以上）→ 只能返回 `climate_statistics`（气候统计参考），**明确标注“非预报数据”**，禁止把窗口外数据冒充预报。
- 失败**不得默认晴天**；天气失败标“天气服务暂不可用，建议出行前自查”。

### 7.6 其余算法速查

| 编号 | 算法 | 一句话 |
|---|---|---|
| ALG-01 | 任务编排与 DAG 调度 | 固定 DAG 依赖执行、可并行分支、幂等重试、进程恢复、终态判定 |
| ALG-03 | 必须确认与不可绕过判定 | 保护项冲突 → 确认生命周期（24h 期限），确认前不写版本 |
| ALG-04 | POI 消歧 | 名称不是主键；必须消歧为 `poi_id + 坐标 + 城市 + 坐标系(GCJ02)` |
| ALG-06 | 路线缓存/直线估算/降级 | 缓存键含坐标系/起终点/方式/时段；估算必须标注 |
| ALG-08 | 知识召回与 RAG 边界 | Chroma 检索 → 回 MySQL 校验发布状态/城市/有效期；只摘录不外推；低置信 → unknown |
| ALG-09 | 预约规则时效 | 超 30 天未核验 → stale，输出“请以官方为准” |
| ALG-11 | 榜单五维加权 | 热度/评分/季节适配/行程合理性/人流量 + 时间衰减 + 人工干预（P1） |
| ALG-12 | 偏好记忆 | 生成后提取稳定偏好 → 权重 + 遗忘 + TOP-K 召回；只作软权重不覆盖当次显式输入（P1） |
| ALG-14 | 缓存键/版本/TTL | 天气按小时、路线按周、景点信息按月、规则按核验；命中与新鲜度对用户透明 |
| ALG-15 | 质量门禁与评估 | 硬约束/来源/保真/时延/成本指标 + 人工评分，见 [methodology.md](docs/evaluation/methodology.md) |

**公共红线（违反即阻断，答辩可直接引用）**：LLM 不生成事实；名称不是主键；估算必须标注且不过硬 Gate；窗口外天气不冒充预报；随机算法固定 seed；每条事实带来源快照；硬约束不可静默违反；已发布版本不可变；Java 是 MySQL 唯一写方。

## 8. 关键逻辑链路逐步走读

### 8.1 一次完整的“生成”之旅（把所有机制串起来）

1. **登录与报价**（已实现）：`POST /api/v1/auth/login` → JWT；`POST /api/v1/points/quotes` 服务端按方案数报价（10/18/25）→ `POST /reserve` 同事务预扣 + 任务 CREATED→BALANCE_RESERVED + 写 Outbox。
2. **入队**：Outbox Relay 发布到 Redis Streams（至少一次），Python Worker 领取（租约）。
3. **解析**（PARSING）：总控把自由文本偏好解析为结构化标签 + 保留原文；可行性预检（5 个必去点塞 1 天 → 直接澄清）。
4. **并行采集**（COLLECTING）：景点资讯（知识库/RAG）∥ 天气（预报窗口分流）∥ 预约规则（时效判定），各自返回带封套 + 来源快照的结果。
5. **日级分配**（SCHEDULING）：基于建议时长/开放时间/天气/预约约束决定“哪天去哪几个点”。
6. **逐日路线**（ROUTING，并行）：ALG-05 贪心+2-opt，逐段路线来自地图 API。
7. **餐饮住宿**：沿确定动线注入每餐候选与每晚住宿。
8. **质量校验**（ASSEMBLING）：ALG-15 检查时间重叠/闭馆/可达/预约/预算/来源/过期；硬冲突走 ALG-02/03 消解或确认。
9. **落版本**：Java 原子创建不可变 `trip_version` + `plan_snapshot` + 字段级 `trip_version_source`。
10. **结算**：SUCCEEDED/PARTIAL 确认预扣（CONFIRM 零值分录）；FAILED/CANCELLED 全额退款（REFUNDED）。
11. **呈现**：前端时间轴展示每个节点的来源、时效、估算/降级徽章（S07 已演示此形态）。

### 8.2 一次“局部修改”之旅

1. 用户：“第二天别安排爬山了，想去博物馆”。
2. 交互修正 Agent：`classify` → `change`；`locate_impact` → affected_days=[2]，可能波及第 3 天顺路点。
3. 若波及必去/锁定项 → `AWAITING_CONFIRMATION` 先确认。
4. 确认后预扣 2 积分 → **只重跑白名单 Agent**（资讯→重排→路线→餐饮），未影响日期原样保留。
5. ETag 校验通过 → 原子创建子版本 + `change_set` → 结构化 diff 给用户 → 终态结算。
6. 用户不满意 → 回滚 = 以任意历史版本为内容来源创建新版本（历史永不修改）。

### 8.3 降级决策树（“降级透明”怎么落地）

```
调用失败 → 有同参数新鲜缓存？→ 用缓存（保留原来源时间）
        → 路线且允许估算？→ 直线估算 is_estimated=true（仅展示，不过硬 Gate）
        → 缺失破坏硬可行性？→ 否：PARTIAL + degraded_fields 列出
                            → 是但可由用户选择：AWAITING_CONFIRMATION
                            → 是且不可绕过：FAILED → 幂等退款 REFUNDED
```

## 12. 答辩 Q&A 预案

**Q1：和直接问 ChatGPT 有什么区别？**
→ 四点：① 它会编造时长/票价/预约政策，我们的事实 100% 来自 API/规则库并携带来源快照；② 它无法结构化局部修改，我们“改一处、不惊动其它”且版本可回滚；③ 它没有实时天气/预约时效治理；④ 我们有沉淀飞轮（榜单/UGC/偏好画像）。

**Q2：和 TripStar 什么关系？重复造轮子吗？**
→ 增量创新而非重复：TripStar 验证了前半段闭环，但有五大缺口（迭代闭环、沉淀层、规划智能靠 LLM 硬扛、预约不成体系、无导出提醒缓存）。我们自研为主体、TripStar 只作效果对照基线，同时规避 GPL-2.0 对外分发传染性。

**Q3：为什么 Java + Python 双栈，不统一技术栈？**
→ 业务侧吃团队 Java 长板，Agent 侧吃 Python 生态（LangGraph/LLM 库）长板；代价用 M0 冻结的 OpenAPI 契约管理，并以“Java 是 MySQL 唯一写方”从架构上隔离一致性风险。

**Q4：为什么中心化编排，不让 Agent 自由协作？**
→ 自由协作的延迟与不确定性对本场景是纯负担；中心化 DAG + 无状态子 Agent 带来可控、可调试、可回放、可降级，符合“工程上可交付”的目标。

**Q5：路线为什么不用 LLM 直接排？**
→ 顺序优化是带时间窗的 TSP 类问题，属确定性组合优化；LLM 排序会出反人类动线且不可复现。我们的分工是：LLM 把柔性偏好翻译为约束，算法求解顺序，结果稳定可解释。

**Q6：数据从哪里来？爬小红书吗？**
→ 彻底不接内容平台抓取（合规决策）：人工运营建库（景区官网/官方公众号等公开资料）+ 未覆盖事实显式留空（不用 LLM 补写）+ UGC 沉淀反哺，三条腿走路。当前落地口径是 M1 仅北京闭环，其余城市按需扩展；未覆盖事实一律显式 `unknown`。

**Q7：8 人 11 周怎么保证不失控？**
→ 契约先行（M0 冻结 Schema/OpenAPI 后完全并行）、S00–S31 步骤流水每步真实证据、每周生成质量评审会、M1 作为风险验证点允许一次方案修订。

**Q8：LLM 成本和延迟怎么控？**
→ DAG 最大化并行、流式进度管理预期、分模型路由（简单任务小模型）、中间产物缓存、多方案共享采集数据、局部修改本身就是最大成本节约（不全量重生成）。虚拟积分建立成本意识。

**Q9：现在做到什么程度了？**
→ 如实答：S00–S04 完成（契约/架构/骨架/39 表数据模型），S05/S06 进行中，S07 开题演示页已交付，S08 认证与积分账务已合入并 32 测试全绿；LLM 网关与 Agent 实现在 S09–S21 按 Gate 推进。设计文档与机器契约已全部冻结。

**Q10：质量怎么保证“不是演示文稿项目”？**
→ ≥30 固定案例评估集（覆盖闭馆/同名 POI/天气窗口/过期规则/局部修改等场景）+ 机器指标（通过率/来源完整率/保真率/时延/成本）+ 双人独立人工评分 + 八层质量保障；证据全部在 docs/progress/，无真实证据不得标记完成。

**Q11：积分体系为什么用虚拟积分？**
→ 建立成本意识又不触碰真实支付合规红线；账务上流水仅追加、幂等守恒（预扣/确认/退款恰好一次），本身也是“可审计大模型应用”的工程范式展示。

**Q12：如果某个 Agent 挂了怎么办？**
→ 重试 1 次 → 降级（该维度缺省并显式标注 degraded_fields）→ 不阻塞整体产出可交付方案；地图失败三级降级（缓存→直线估算标注→失败）；全链路失败可见、可一键重试、积分全额退回。

### 14.3 四个深水区（评委追问最终会落到这里）

#### 深水区一：任务状态机（你画得出来吗？）

```
CREATED → BALANCE_RESERVED → QUEUED → PARSING → COLLECTING → SCHEDULING
→ ROUTING → ASSEMBLING → AWAITING_CONFIRMATION
→ SUCCEEDED / PARTIAL / FAILED / CANCELLED → REFUNDED
```

- **为什么 15 态不能简化**：每态对应一个可恢复的检查点、一类失败去向和一个结算语义。比如 `BALANCE_RESERVED` 单独存在，是为了解耦“扣费成功”与“入队执行”——崩溃恢复时能区分该退款还是该续跑。
- **谁驱动迁移**：Java 侧校验命令并用乐观锁 CAS（条件 UPDATE + `state_version` + 影响行数检查）推进状态；Python 汇报步骤结果但**不能直接改状态**。
- **崩溃恢复**：`task_step` 带租约（`lease_owner/lease_expires_at/heartbeat_at`）+ `attempt_no`；Worker 崩溃 → 租约过期 → 只增加 attempt 重跑，**不能重复创建版本、重复结算、重复发通知**。恢复以 MySQL 状态和成功步骤为准，来源仍新鲜则复用，否则从最早受影响步骤重跑。
- **时限**：PARSING 30s、COLLECTING 60s、首次生成全局 180s、局部修改 60s、确认等待 24h（暂停执行 Deadline）。
- **终态结算触发点**：终态只结算一次——SUCCEEDED/PARTIAL 确认预扣，FAILED/CANCELLED 退款。R1 定义触发点，账务实现在 R5（[ALG-13](docs/多智能体协作文旅规划平台-算法设计说明书.md) 4.13）。

#### 深水区二：事务 Outbox + Redis Streams（分布式一致性的标准答案）

- **要解决的问题**：“扣费成功但任务没执行”与“任务执行了但没扣费”。
- **错误做法**：业务事务里直接 `redis.send()`——进程在发送后崩溃，消息丢失且不可追溯。
- **正确做法**（ADR-0002）：任务创建 + 积分预扣 + `outbox_event` 写入**同一 MySQL 事务**提交 → Outbox Relay 只读已提交事件，**至少一次**发布到 Redis Streams Consumer Group → Python Worker 消费（租约领取）。
- **至少一次 ≠ 恰好一次**：投递可能重复，靠消费侧幂等兜底——`planning_task.idempotency_key`、`outbox_event.idempotency_key`、`agent_result.idempotency_key` 唯一索引，重复消息返回原结果（`reused=true`）。
- **为什么 SSE 不用 WebSocket**（ADR-0003）：进度是单向流、命令走 REST 即可；SSE 天然穿 HTTP 代理、配合 JWT 简单。断线恢复靠 `task_event.sequence_no` 单调递增，前端从最后序号补拉并按 `(task_id, sequence_no)` 去重。
- **为什么不用 Kafka**：单机部署、10~20 并发规模，Redis Streams 足够；MySQL 是事实源，Redis 只传递、随时可重建。

#### 深水区三：冲突消解与人工确认（ADR-0011，总控裁决权的落地规则）

- **六级硬约束优先级**：显式硬约束（必去/锁定/已确认选择）> 闭馆/预约/开放时间 > 可达与时间窗 > 天气安全 > 预算上限 > 软偏好。**高优先级不代表可违反客观可行性**：必去点闭馆时不得安排闭馆时段、也不得静默删必去点，必须转确认并给有来源的选项。
- **确定性四步消解**（不涉保护项时）：同日换序 → 同城同类替换 → 跨日互换 → 删最低软偏好项；每个候选都要**重新验证**开放时间/可达/预算/来源。
- **必须确认的 6 条件**：动必去/锁定/固定起终点；动已确认预约或跨日；所有可行解都超硬约束；影响范围无法唯一确定；基于旧版本的修改；多个可行方案需用户权衡代价。
- **不可绕过（直接失败/澄清，不给“仍然继续”）**：身份/归属/余额/幂等/版本校验失败；必需事实无合法来源或 Schema 修复后仍无效；路线不可达且无可验证替代；范围外能力（真实支付/代订/爬取）。
- **确认生命周期**：`task_id + confirmation_revision` 只接受一次决定（幂等）；拒绝/24h 无响应 → CANCELLED（有预扣则退款），**超时不自动选默认项**；确认期间版本变更 → 旧确认失效、409、不执行不扣费。
- **总控五不**：不删必去/锁定项、不改城市日期、不用过期事实作硬约束、不让直线估算过可行 Gate、**不用自然语言掩盖结构化冲突**。

#### 深水区四：契约治理（“契约先行”怎么落地成 CI）

- **封套设计的关键**：`schema_version/task_id/trace_id/request_id/generated_at/source_metadata` 由服务封装层注入，**模型只生成 `status` + 专属载荷**——模型无法伪造来源（反幻觉在契约层的体现）。
- **冻结内容**（S02）：7×2 个 Schema（Draft-07）、28 个四态样例、`agent-business.yaml`、错误码目录、[agent-contract-index.md](contracts/agent-contract-index.md)。
- **CI 门禁**：Draft-07 校验、样例校验、OpenAPI 破坏性检测、Java/Python 消费者兼容测试。
- **变更流程（背下来）**：Schema 与示例 → 契约测试 → prompt → 实现与消费者；发现破坏性问题**先列清单，不私自改语义**；已接受的决策要改就**新建 ADR 并把旧的标 Superseded**，不抹历史。
- **Schema 修改未通知消费者**是规范里写明的**阻断错误**之一。

### 14.4 R1 编排规则速查（来自 R1 规范 §3–4）

- 调度只传**最小必要数据**，按依赖 DAG 执行；每步写 `task_step(task_id, step_name, attempt_no, status, input_hash, output_ref)`。
- 结果合并是**确定性规则**（即六级优先级）；总控的解释文案**不得覆盖事实字段**。
- 子 Agent 部分失败继续生成，汇总 `degraded_fields`；路线失败先精确缓存、再标直线估算；无可行行程/非法模型输出/余额版本冲突进入明确终态。
- 局部修改输入必须含 `base_version` + 用户锁定项 + 指令；确认前不创建发布版本；确认后只调度影响范围内 Agent，未受影响快照保持不变。
- 进度事件单调 `sequence_no`，断线前端补拉。

### 14.5 R1 验收清单与阻断错误（规范 §5，答辩可当“质量观”讲）

**必须覆盖的测试**：DAG 执行、状态迁移合法性、重复消息、乱序进度、取消、进程恢复、每种 Agent 失败、确认超时、并发修改（旧 ETag 409）。

**六类阻断错误**（出现即 Gate 不通过）：
1. 子 Agent 直连用户或数据库；
2. 用自然语言代替结构化状态；
3. 部分结果未标识（降级静默）；
4. 以全量重生成代替局部修改；
5. 按前端状态决定退款；
6. Schema 修改未通知消费者。

### 14.6 R1 答辩深挖题（12+2 道，每题给答题要点）

**Q1：为什么中心化编排，不让 7 个 Agent 自由协作？**
→ 自由协作适合开放探索，不适合“可控交付”：我们的链路要求可调试、可回放、可降级、可计费。总控唯一对外、子 Agent 无状态不互连，换来确定的延迟与失败边界。LangGraph 的图式编排 + 状态持久化与这个模型天然契合（对比 HelloAgents 的字符串协议工具调用易碎、无状态持久化）。

**Q2：状态机为什么要 15 个状态？是不是过度设计？**
→ 每态是一个可恢复检查点 + 一类失败去向 + 一个结算语义。举例：BALANCE_RESERVED 与 QUEUED 分离，才能在崩溃恢复时区分“已扣费待执行”（续跑）与“未扣费”（不用退）；AWAITING_CONFIRMATION 独立存在，才能实现“确认前不写版本”。状态数由业务不变量反推，不是为多而多。

**Q3：Redis 至少一次投递，怎么保证不重复扣费、不重复生成？**
→ 三层幂等：HTTP 头 Idempotency-Key → 业务 reference 命名空间（`reserve:{task}` 等）+ 流水唯一索引 → DB 唯一约束兜底。重复消息查到已有结果直接返回（reused=true）；任务侧 `idempotency_key` 唯一索引 + 租约防重复领取；终态只结算一次。

**Q4：为什么进度用 SSE 不用 WebSocket？**
→ 进度是单向推送、命令走 REST，SSE 够用且更简单（穿代理、配 JWT、自动重连）。断线不丢进度：事件仅追加 + sequence_no 单调，客户端补拉去重。WebSocket 的双向能力我们不需要。

**Q5：为什么不让 Python Agent 服务直接写 MySQL？**
→ ADR-0001：双栈下“两个服务写同一库”会产生隐性耦合（事务边界、迁移节奏、锁语义互相牵制）。Java 唯一写方后，一致性责任集中一处，Python 失败可重放、不影响业务事实。代价是多一跳 REST 回写，用契约和幂等把它管住。

**Q6：8 个人并行开发，接口怎么对齐？中途改契约怎么办？**
→ M0 先冻结 Schema/OpenAPI + 四态样例 + 消费者测试入 CI，之后各角色完全并行（R2/R3/R4 还能用 Mock 数据源独立开发）。变更走固定顺序：Schema 与示例→契约测试→prompt→实现与消费者；破坏性问题先列清单、R1 终审，不许私自改语义。

**Q7：“总控有最终裁决权”和“不得用自然语言掩盖结构化冲突”矛盾吗？**
→ 不矛盾。裁决权是在**确定性规则内**选候选（六级优先级 + 四步消解），裁决结果必须是结构化的（change_set、冲突代码），文案只是解释。裁决权的边界是硬约束：必去点闭馆这种客观不可行，总控不能“说服自己”，必须转确认让用户选。

**Q8：确认超时为什么不做默认选择？24 小时怎么定的？**
→ 自动选默认项等于替用户承担行程风险（尤其涉及删必去点/花钱），拒绝和超时都回到原版本最安全。24h 是“一天内会回来看”的产品假设 + 可配置参数（PENDING 项之一）；确认等待暂停全局 Deadline，不占执行时限。

**Q9：为什么版本不可变？回滚为什么是新建版本？**
→ 可审计与可复现：任何一次生成/修改都能还原“当时看到的计划 + 当时的来源快照”。原地修改会破坏历史证据链（审计、积分结算依据、diff 对比基线）。回滚以历史版本为内容来源创建新版本，版本链（parent_version_id + change_set）完整保留演进过程。

**Q10：LangGraph 在实现里具体承担什么？**
→ 图式编排（首次生成/局部修改两张固定 DAG）、状态持久化与断点续跑（配合 task_step 的 input_hash/output_ref 从任一步恢复）、human-in-the-loop（AWAITING_CONFIRMATION 挂起等待用户）。注意口径：图与状态机**设计已冻结**，代码实现排在 S19（R1-03/R1-04）。

**Q11：你个人在项目里具体做了什么？**
→ 按证据答：S00 仓库治理与需求追踪矩阵、S01 范围审计/11 篇 ADR/状态机/冲突消解规则、S02 契约冻结与终审（7 Schema + OpenAPI + 四态样例 + 错误码）、S03–S04 评审与验收配合，证据都在 [docs/progress/](docs/progress/)；下一步 S19 编排实现由我主责。

**Q12：架构上最大的风险是什么？你的应对？**
→ 两个：① 多 Agent 链路延迟与失败叠加（应对：DAG 并行、降级不阻塞、流式进度、局部修改避免全量重生成、180s/60s 全局 Deadline）；② 8 人集成期契约漂移（应对：契约先行 + 破坏性检测 CI + Mock 数据源 + M1 尽早端到端）。模型效果风险由 M1 Gate 验证并允许一次方案修订。

**Q13：degraded_fields 是谁填的？怎么保证降级一定可见？**
→ 子 Agent 按各自降级策略产生，总控汇总到输出封套；封套在 Schema 层强制——partial/degraded 时 `degraded_fields` 必须非空（minItems 1），failed 必须有 error_code + message。前端 S07 演示页已有 partial 态展示，评估指标里还有“降级可见率”机器校验。

**Q14（开放题）：如果重做一次，会改什么？**
→ 参考方向（诚实且显示思考深度）：状态机里 PENDING 参数（tie-break、权重、预算档费率）应该更早冻结；评估集可以和契约同批启动以便更早量化；本地模型路线可以更早做小规模验证。注意别说“推翻双栈/中心化”——那是被论证过的决策。
