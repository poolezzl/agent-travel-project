## 2. 冻结结论摘要

### 2.1 统一物理规则

- 所有 UUID 主键、外键和关联键统一为 `BINARY(16)`；应用层负责 UUID 与二进制值互转，禁止同一关联混用 `CHAR(36)` 和二进制类型。
- MySQL 8、InnoDB、`utf8mb4`、UTC `DATETIME(6)` 是所有表的统一基础。
- Java/Spring Boot 是 MySQL 业务数据唯一写方；Python Agent、前端和 Redis 不得直连业务表。
- 业务表使用小写 `snake_case` 物理表名和字段名。
- `created_at`、`updated_at` 使用 UTC；不可变/追加表不提供业务更新接口。
- JSON 仅保存不可稳定查询的正文、扩展载荷或脱敏摘要；owner、状态、版本、时间、幂等、金额、来源身份等可查询字段必须列化。
- 已发布版本、计划快照、来源快照、任务事件、Agent 结果、积分流水、审计事件和对象元数据的身份字段不可修改；修订、纠正或回滚均通过新记录完成。

## 3. 最终决策与依据

| 决策项 | 最终设计 | 依据与物理实现说明 |
|---|---|---|
| 正式表名 | 使用第 2.2 节 40 张表 | S04 数据域目标、需求追踪矩阵、ADR-0004/0005、R8 社区规范；具体物理命名属于 R5 授权的 S04 物理实现决策 |
| UUID | 全部 `BINARY(16)` | 官方只冻结 UUID 语义未冻结物理类型；为统一索引、FK 和 ORM，按 R5 授权选择最小统一方案 |
| 行程拆分 | `trip` 保存 owner/标题/城市/日期和 current version；`trip_version` 保存不可变版本元数据；`plan_snapshot` 与版本一对一保存正文；`change_set` 与版本一对多保存结构化变更 | ADR-0005、REQ-2.3.1、Revision Schema；正文不与版本元数据混在单表，回滚创建新版本 |
| 版本一致性 | `trip_version.parent_version_id`、`plan_snapshot.trip_version_id`、`change_set.trip_version_id` 关联同一 trip；跨行一致性由同一事务的 Java 校验保证 | ADR-0005；MySQL 普通 FK 无法表达跨表同 trip 复合断言，禁止依赖静默放宽 |
| 来源拆分 | `source_record` 是稳定来源身份；`source_snapshot` 是一次取得的不可变内容快照 | ADR-0004、Agent `source_metadata`、S10/S15 来源要求 |
| Agent 幂等 | `agent_result.request_id` 全局唯一；同时保存 `request_hash BINARY(32)`；同 request ID 同 hash 返回原结果，不同 hash 拒绝；`idempotency_key` 在 `(task_id, step_id)` 范围唯一 | OpenAPI `Idempotency-Key`、Agent Contract Index、`DUPLICATE_REQUEST`；全局唯一是本次 R5 授权的稳定实现决策 |
| 积分报价 | 独立 `points_quote`；任务引用实际 quote；quote 有过期和一次接受状态；预扣/确认/退款只写 `points_ledger` | ADR-0002、ADR-0007、DEC-016/017/025、任务状态机 |
| Outbox | 保留 `aggregate_type + aggregate_id` 多态引用，不建业务 FK；使用聚合白名单、业务校验和 `(aggregate_type, aggregate_id, idempotency_key)` 唯一 | ADR-0002 要求事务 Outbox，且 Outbox 跨任务/积分/版本聚合；多态无 FK 是 R5 授权的物理实现决策 |
| 步骤输出 | `task_step.output_result_id` 可空 FK 指向 `agent_result.id`；迁移顺序先建 task/step 和 result，再补 FK，允许循环关系安全落库 | Agent 结果契约、S11 任务恢复要求；结果表仍保留 task/step 双 FK 作为一致性锚点 |
| P1 表 | 按本任务明确的 S04 首版正式范围冻结社区、偏好、导出、提醒结构；不实现其业务 API | 需求追踪矩阵、S04 任务明确范围、S23-S28 后续实现边界；这是“结构冻结”，不是提前实现 P1 |
| Redis | 只冻结 key/version/TTL 契约，不在 MySQL 建 Redis 表，不把缓存当事实源 | ADR-0006、REQ-2.5.3、ADR-0002 |
| 审计载荷 | 只允许白名单脱敏字段，禁止密码、Token、完整供应商响应、原始 Prompt、精确住宿和敏感偏好 | ADR-0001、ADR-0004、错误码规范、R5/R8 规范 |

## 4. ER 关系与基数

### 4.1 账号、行程和版本

- `user_account 1:N user_session`：会话属于用户，refresh token 只保存哈希。
- `user_account 1:N trip`：行程 owner 为用户；ADMIN 仅按授权访问，不改变 owner。
- `trip 1:N trip_city`、`city 1:N trip_city`：行程通过有序关联表表达单城市或多城市串联，`sequence_no` 是行程内城市顺序。
- `trip 1:N trip_version`：行程版本只追加；`trip.current_version_id` 指向当前有效版本。
- `trip_version 1:1 plan_snapshot`：每个版本恰有一个不可变计划正文快照。
- `trip_version 1:N change_set`：版本可有多个原子变更记录；回滚仍创建新版本和新 change set。
- `trip_version N:M source_snapshot`：通过 `trip_version_source` 保存字段路径级来源引用。

### 4.2 来源、任务和 Agent

- `source_record 1:N source_snapshot`：稳定来源身份对应多次取得快照。
- `planning_task 1:N task_step`、`planning_task 1:N task_event`：任务拥有步骤和追加事件。
- `task_step 1:N agent_result`：每个步骤按 attempt 保存结果；当前输出通过 `output_result_id` 指向一个结果。
- `agent_result N:M source_snapshot`：通过 `agent_result_source` 关联事实来源。
- `outbox_event` 以 `aggregate_type + aggregate_id` 引用任务、积分或版本聚合，不建立跨聚合 FK。

### 4.3 城市、POI、知识和预约规则

- `city 1:N poi`；`poi 1:N poi_snapshot`；`poi 1:N poi_alias`。
- `poi 1:N knowledge_entry`；`knowledge_entry 1:N knowledge_chunk`。
- `poi 1:N reservation_rule`；规则自身按 `rule_key + version_no` 版本化。
- POI、知识、规则均通过 `source_snapshot` 追溯；Chroma 只持有索引，MySQL 持有审核状态和事实元数据。

### 4.4 积分

- `user_account 1:1 points_account`。
- `user_account 1:N points_quote`、`planning_task 0..1:1 points_quote`。
- `points_account 1:N points_ledger`；流水同时保留 user/task/quote 业务关联并由 Java 校验归属一致。
- quote、reserve、confirm、refund 使用不同且唯一的 `business_reference`，不更新或删除历史流水。

### 4.5 社区、偏好、导出和提醒

- `trip_version 1:N post`：帖子只能引用已存在的行程版本；发布内容为脱敏副本。
- `post 1:N post_comment`；`post_comment` 通过 `parent_comment_id` 自引用，支持可选评论树。
- `post N:M user_account` 通过 `interaction` 关联；同一用户同一帖子同一互动类型只有一条可恢复记录。
- `post/post_comment N:M report` 以 `target_type + target_id` 表达举报目标；多个举报可归并到一个 `moderation_case`。
- `moderation_case` 管理一个目标的一次治理案件；`ranking_entry` 是基于已公开且未下架帖子生成的可重建派生记录。
- `user_account 1:N user_preference`；`user_preference 1:N preference_evidence`；`user_account 1:N preference_summary`。
- `user_account 1:N object_metadata`；`export_job N:1 object_metadata`，导出文件不写入 MySQL 正文。
- `user_account 1:N reminder_candidate`；`reminder_candidate 1:N notification`，通知仅站内。
- `user_account 1:N audit_event`，actor 可为空以保留系统事件。

## 5. 首版正式表数据字典

约定：所有列出的 UUID 类型均为 `BINARY(16)`；所有 `DATETIME(6)` 为 UTC；所有表均为 InnoDB/utf8mb4。`PK` 主键，`FK` 外键，`UQ` 唯一键，`CK` 检查约束，`IDX` 普通索引。JSON 列不承载 owner、状态、版本、时间和授权判断。

## 6. owner、权限、审计、保留与删除矩阵

| 账号/会话 | 用户本人；ADMIN 按接口授权 | 账号状态、会话吊销可更新；密码只写哈希 | 用户删除时账号转 `DELETED`，会话吊销并清除 token hash；账号审计保留 |

### 6.1 删除和匿名化原则

- 不使用级联物理删除破坏版本、来源、账务、治理或审计证据。
- owner 删除优先采用 tombstone/匿名化：`user_account` 保留不可登录的 `DELETED` 行；需要保留历史关联的表保留 FK。
- 用户可识别字段、私有正文、偏好 JSON、精确住宿和下载 token 按域清除或不可逆脱敏；公开帖子在保留治理证据的前提下撤回并去标识。
- `points_ledger`、`audit_event`、已引用 `source_snapshot`、已发布 `trip_version` 不因用户删除物理删除。

## 8. Redis key/version/TTL 契约边界

Redis 不进入 MySQL migration。所有 key 由 Java/适配器按统一版本契约生成，队列、缓存、限流前缀严格分离：

| 域 | Key 形式 | version 字段 | TTL/失效规则 | MySQL 边界 |
|---|---|---|---|---|
| 任务队列 | `queue:v1:task:{task_id}` | `v1` | Streams/消费组语义；不以 TTL 替代 task_event | `planning_task/task_step/task_event/outbox_event` 是事实源 |
| 路线缓存 | `cache:v1:route:{provider}:{coord_sys}:{origin_hash}:{destination_hash}:{mode}:{time_window}` | key 和 payload 均含 `v1`、retrieved_at、valid_until | 默认 7 天；参数变化必须换 key；失败鉴权不缓存 | `source_record/source_snapshot` 保存被采用的事实摘要，不保存 Redis 缓存本体 |
| 天气缓存 | `cache:v1:weather:{provider}:{city_id}:{date_range}:{forecast_window}` | key/payload 含 `v1`、实际 forecast window | 默认 1 小时；过期只返回 stale/unknown，不伪造晴天 | 采用的来源快照写 MySQL |
| POI 缓存 | `cache:v1:poi:{provider}:{city_id}:{external_poi_id}` | key/payload 含 `v1`、source version | 默认 30 天；发布/停用主动失效 | POI/POI snapshot 是事实源 |
| 知识/规则缓存 | `cache:v1:knowledge:{city_id}:{knowledge_entry_id}:{version_no}`、`cache:v1:rule:{poi_id}:{rule_key}:{version_no}` | 必须带 entry/rule version | 已发布版本有效期由 `effective_until` 和 stale 规则决定；发布/停用失效 | MySQL 已发布知识/规则是事实源 |
| 限流 | `rate:v1:{scope}:{subject}:{operation}` | `v1` | 按接口窗口配置；不与缓存复用前缀 | 不写业务事实表 |

缓存 payload 必须包含 `retrieved_at`、`valid_until`、`freshness_status`、`is_estimated` 和 provider/version 元数据；Redis 丢失时可从 MySQL 来源事实重建或返回 unknown。不得缓存鉴权失败、敏感用户请求或把缓存命中当作发布事实。

## 10. 实施前一致性修订记录

在生成正式 migration 前复核官方需求和冻结单，确认以下内容必须修订后才能形成可验证 DDL：

| 原问题 | 官方依据 | 修订结论 | 对正式表范围的影响 |
|---|---|---|---|
| `trip.city_id` 只能表达单城市，但需求要求城市列表顺序和多城市串联 | `docs/01-需求与整体设计.md` 2.1 输入定义；`docs/04-逐步开发提示词.md` S04 | 删除 `trip.city_id` 作为城市事实列，新增 `trip_city(trip_id, city_id, sequence_no)`，单城市也是一行 | 正式表由 39 张变为 40 张 |
| `reminder_candidate.source_rule_id` 无法同时验证预约规则和天气来源 | `docs/04-逐步开发提示词.md` S17/S26；ADR-0004 | 改为 `source_type` 加 `reservation_rule_id`/`source_snapshot_id` 两个可空 FK，并用 CHECK 要求按类型恰有一个来源 | 不新增表；来源引用可验证 |
| `trip_version.content_hash` 唯一性描述不一致 | ADR-0005 版本身份语义；冻结单原文字段表 | 统一为同一 `trip_id` 内 `(trip_id, content_hash)` 唯一，跨行程允许相同正文哈希 | 不新增表；唯一键统一 |
| `trip`、`trip_version`、`poi`、`poi_snapshot`、`task_step`、`agent_result` 存在循环引用 | MySQL 8 DDL 约束能力；S04 migration 可重复验证要求 | 分阶段建表，最后用 `ALTER TABLE` 补 `current_version_id`、`current_snapshot_id`、`output_result_id` 外键 | 不改变业务关系 |

以上修订均是使已要求的数据域可表达、可验证的物理实现决策，不实现业务 API、状态机或第三方调用。
