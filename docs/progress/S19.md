## 关键设计

### 固定 DAG 与 Java 状态机一一对应

| 阶段 | Java 状态/步骤 | 行为 |
|---|---|---|
| parse | `PARSING` / `parse` | 校验城市、日期、预算、必去点；非法输入返回 `INVALID_INPUT` |
| collect | `COLLECTING` / `collect` | 资讯、天气、预约三路并行；单路失败只降级本切片 |
| schedule | `SCHEDULING` / `schedule` | 按闭馆日与游览时长分配日期；必去点绝不静默删除 |
| route | `ROUTING` / `route` | 复用 S12 `plan_route`；逐日并行；直线估算标 `is_estimated` |
| assemble | `ASSEMBLING` / `assemble` | 餐住整合、质量检查、冲突汇总、最终 Plan |

Java 每步把已持久化的上游 `agent_result` 作为 `prior` 传给 Python；Python 不自行读库，
继续满足“Java 是 MySQL 唯一写入方”。

### 冲突与确认

- 必去点未收录/同名/全部闭馆/无坐标、预算硬上限被突破、路线或时间窗不可行且影响必去点，
  都会生成 `severity=blocking` 的冲突与可选方案。
- `confirmation.required=true` 时 Java 只把任务转为 `AWAITING_CONFIRMATION`、写 24 小时
  截止时间和事件，**不创建任何版本、不确认积分**；`/plan` 返回 409
  `CONFIRMATION_REQUIRED`。接受/拒绝命令属于 S20，未在本步提前实现。
- 估算路段只作为展示，质量检查明确“不视为硬可行”，不冒充精确路线。

### 不可变版本与幂等

- 版本内容使用 `CanonicalJson` 排序序列化后取 SHA-256；`trip_version.content_hash`
  命中已有版本时复用，不重复插入。
- `version_no` 按 trip 递增，`etag` 由 `trip_id + version_no + content_hash` 派生并满足
  全局唯一约束；`plan_snapshot` 与版本同事务写入，`trip.current_version_id` 同步更新。
- 积分确认使用 `task-confirm:{taskId}` 幂等键，重复提交返回既有流水。
- assemble 失败时沿用 `TaskTerminationService` 退款路径；确认分支不退款（等待用户决定）。

### 质量检查

`TIME_OVERLAP`、`OPENING_HOURS`、`REACHABILITY`、`RESERVATION`、`BUDGET`、
`FRESHNESS`、`SOURCES`、`MUST_VISIT_MISSING`。任何 blocking 冲突或 `quality=fail`
都不会生成版本；过期天气/规则只降级并在 Plan 中显式展示。

## 来源 / 权限 / 幂等 / 并发 / 降级 / 隐私 / 回滚

- 来源：知识事实带 `chunk_id + source_record_id`，预约带 `policy_id + source_record_id`，
  路线 leg 带 `source_record_id/retrieved_at/is_estimated`；天气无效时不生成事实。
- 权限：`/plan` 校验任务 owner 或 ADMIN；非 owner 统一 404，避免枚举。
- 幂等：版本按 content_hash 复用；积分确认用 `task-confirm:{taskId}`；Python 阶段对相同
  输入字节返回相同输出。
- 并发：assemble 复用 `planning_task` 行锁与 `state_version` CAS；取消与版本提交以事务
  先后决胜。
- 降级：子 Agent 的 partial/degraded 通过 `degraded_fields` 汇总；weather/route 缺失显式
  可见；估算不通过硬可行性。
- 隐私：请求日志不记录 Prompt/API Key/完整私密行程；Plan 只保存行程内容与来源摘要；
  未新增真实用户或供应商原始响应。
- 回滚：删除 S19 契约/示例、`app/orchestrator/`、`api/planning.py`、Java 六个 S19 类与
  测试、前端 Plan 相关改动即可；无新增数据库迁移（复用 V1 既有表）。
