## 验收任务

| 任务 | 实现与验收条件 |
| --- | --- |
| 问答和澄清 | Java 从有归属权限的版本读取行程，调用 Python 修正 Agent。事实不足时说明缺失。问答和澄清的余额、版本保持原值。 |
| 局部修改 | 预览返回原子变更和影响范围。确认后只执行所列日期和 Agent。其他日期逐字段一致。当前支持指定景点增加、替换、删除、路线重排、两日互换和明确选择已有住宿候选。无法定位的请求返回澄清或可行性错误。 |
| 版本和积分 | 变更由服务端生成。每次成功确认消费 2 积分。失败事务撤销预扣和版本写入。并发重复确认返回同一版本。过期 ETag 返回 409。 |
| 回滚 | 以当前版本为父版本，以指定历史版本内容为新版本内容。保留历史并复用目标版本已有的来源关联。V3 允许不同版本使用相同内容哈希，ETag 仍按版本区分。 |
| 多方案 | 普通生成任务按服务端已报价的数量返回 1 至 3 套。多套共享一次采集结果并剔除过期事实，每套执行质量检查。不同节奏、路线或已知票价优先级必须落到实际计划。无法生成足量不同方案时进入现有失败退款流程。 |

## 接口与运行

- `POST /api/v1/trips/{tripId}/revisions/preview` 接收 `base_version_id` 和
  `revision_request`。发生修改时需提供当前 `etag`。
- `POST /api/v1/trips/{tripId}/revisions/confirm` 接收原始请求、基准 ETag、
  `confirmed`、`confirmation_id` 和同值的 `Idempotency-Key` 请求头。
- `POST /api/v1/trips/{tripId}/revisions/rollback/{versionId}` 接收当前版本
  `If-Match`。成功后可通过现有行程读取接口取回新版本。
- 多方案使用现有 `POST /api/v1/tasks` 提交 `plan_count`。通过
  `GET /api/v1/tasks/{taskId}/plan` 的 `summary.variants` 读取计划、共同采集哈希、
  已知成本、策略运行耗时和质量分。
- Java 的 `AGENT_SERVICE_BASE_URL` 指向 Python Agent 服务。接口契约见
  `contracts/openapi/s20-revisions.yaml` 与 `contracts/openapi/s11-tasks.yaml`。
- 已发布版本保留计划中的来源元数据和已有数据库来源关联。多方案共用已持久化的
  `collect` 步骤结果。对话前端、确认弹窗和 diff 交互由 S21 交付。
