## 接口、Schema 与迁移影响

- 无 OpenAPI 破坏性变更：队列消息是 Outbox/Redis Streams 内部载荷，新增只读字段 `sequence_no`；
  旧消息缺少该字段时按 0 处理（视为“无序号”，不参与水位比较）。
- `POST /api/v1/points/refund` 语义收紧：任务预扣只能由任务状态机退款，直接调用返回
  `409 CONCURRENCY_CONFLICT`（错误码取自 `contracts/error-codes/error-codes.md` 既有条目）。
- 新增 Flyway `V4`（仅新增列，默认 0，不改写 V1-V3）；已在空库真实执行到 V4。
- 评估器不新增 HTTP 接口；`tests/evaluation/*` 不是服务契约。

## 关键设计

### 1. 30 案例离线全链路评估

`tests/evaluation/s22_gate.py` 对每个案例：

1. 按案例契约（城市、日期、`allowed_source_record_ids`、`expected_behaviors`）确定性生成一份
   **合成已发布快照**（`sample_only=true`），来源 ID 严格取自该案例白名单；
2. 用真实 S19 代码跑 `parse → collect → schedule → route → assemble`，并用
   `contracts/s19/plan.schema.json` 校验最终 Plan；
3. 从 Plan 抽取事实槽位（景点事实、天气、预约、路段），记录来源、鲜度、估算与显隐状态；
4. 对声明局部修改的案例调用真实 S20 `revision_execution.apply`，对比未影响日期的规范化哈希；
5. 输出 `metrics.py` 约定的脱敏记录，再聚合成 M2 指标并逐项判定门槛。

**通过定义**（写入本文件与 `m2-gate.json`）：固定 DAG 无步骤失败 + Plan 通过 Schema + 该案例所有
`expected_behaviors` 成立 + 全部硬约束成立 + 事实来源均在白名单内。`plan.quality.status=fail`
不视为流水线失败——闭馆/同名等案例的契约就是“阻断冲突 + 等待用户确认”。

### 2. 演练补齐

| 演练 | 实现 | 本次证据 |
| --- | --- | --- |
| 任务取消 | 既有 `TaskService.cancel`；新增退款后清理预扣 | 单测 + MySQL IT `cancellingQueuedTaskRefundsOnceAndClearsTheReservation`（余额回 100、仅 1 条 REFUND、重复取消不再退款） |
| 崩溃/租约恢复 | 既有 `TaskWorkerClaimService` 租约与 `outputFresh` 逻辑 | 既有单测 `expiredLeaseIsRecoveredBeforeAnotherAttemptStarts`、`staleLeaseOwnerCannotCompleteAnotherWorkersStep`（本步未新增，进程级 kill 演练留 S29） |
| 确认超时 | 新增 sweeper：到期 `AWAITING_CONFIRMATION → CANCELLED → REFUNDED`，行锁下重判 | 单测 2 条 + MySQL IT `confirmationTimeoutRefundsOnceAndClosesTheTask`（余额回 100、1 条 REFUND、1 条超时 Outbox、二次扫描不重复退款） |
| 重复/乱序消息 | `QueueMessage.sequenceNo` + V4 水位 + 消费端丢弃 `sequence ≤ last` | 单测 `consumerDropsDuplicateAndOutOfOrderQueueMessages` + Redis IT `realQueuePublishesAndReadsTheSequenceNumber` + MySQL IT `queueSequenceWatermarkRejectsDuplicatesAndRegressions` |
| 各 Agent 故障 | 天气不可用、路线供应商超时、知识/规则缺失、餐住 POI 源异常 | `test_s22_robustness.py` 4 条 + 既有 S11 状态映射单测（ok/partial/degraded/failed） |
| 终态只结算一次 | 既有 `confirm/refund` 幂等；修复 `settleRevision` 并发重复扣费 | MySQL IT `repeatedSettlementWritesOneConfirmRowAndRejectsRefundAfterwards` + 单测 `revisionSettlementChargesOnlyOnceForTheSameFingerprint` |

### 3. 评估暴露并修复的编排缺陷

- `collect` 未把注入时钟传给景点/预约子 Agent → 知识库与规则用墙钟判鲜度，同一输入在不同日期
  结论不同（M2 要求可重复）。已改为传入 `deps.now()`。
- `quality` 从 route 日对象读 `weather`（该对象没有天气字段）→ 每个 Plan 都被误标“天气未知”，
  既虚报降级又掩盖真实过期。已改为读取 collect 的真实天气切片。
- 直线估算路段时间戳取墙钟 → 相同输入 Plan 字节不同。已改为注入时钟。

## 检查清单

- 来源：所有事实携带 `source_record_id`，且均属于该案例白名单；合成数据显式 `sample_only`。
- 权限：退款接口区分任务状态机与用户自助；评估器不含任何用户数据或凭证。
- 幂等：队列序号水位、任务事件唯一序列、积分 `business_reference`、修订指纹四层。
- 并发：任务行锁 + 账号行锁；超时扫描在行锁内二次判定；重复确认复用版本。
- 降级：天气不可用、路线超时、知识/规则缺失、餐住源异常均有显式降级字段与用户可见说明。
- 隐私/日志：评估记录只含合成来源 ID、布尔、计数与哈希；不保存 Prompt、私密行程或供应商原始响应。
- 回滚：本步仅新增 V4 列与后台扫描，可通过关闭 `app.s11.confirmation-sweep-enabled`、
  回滚分支与 `V4` 的 `DROP COLUMN`（仅限未发布环境）回退；不存在已发布迁移改写。
