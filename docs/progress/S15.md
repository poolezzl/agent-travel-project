## 关键设计

- MySQL/Java 是事实与审核状态唯一来源；Chroma 只由 Agent 服务拥有，索引滞后时宁可返回 unknown（ADR-0008）。
- 检索只返回 `PUBLISHED`、城市匹配、未过期的 chunk，并携带 `knowledge_id/chunk_id/source_record_id/retrieved_at`；Chroma 侧同时用 `effective_until_epoch` 与最低分过滤。
- 同名/同别名多 POI 不自动合并，交人工队列；管理端必须显式 `MERGE` 或 `REJECT`，两种情况都写审计，`MERGE` 只写 `merge_group_id`，不删除任一 POI。
- 知识/规则发布、停用、回滚保留历史版本。
- 预约规则 `stale` 由 `last_verified_at` 与 `stale_after_days` 计算，LLM 不参与；缺价保留 unknown，不用 0。
- 导入只产生 draft，必须复核后发布；来源缺少许可/URL 的记录拒绝进入可读集合。
- `knowledge_entry.content_hash` 直接写 32-byte SHA-256，匹配 `BINARY(32)`；POI 导入缺少 `external_poi_id` 时生成 `import-` 前缀临时值，避免真实库 NOT NULL 失败。

### 幂等性

脚本在每次 preview/commit 前按 `poi.external_poi_id`、`knowledge_entry.entry_key`、
`reservation_rule.rule_key` 与来源快照做只读存在性检查，只提交缺失行；连续两次执行的
行数完全一致：

```text
before:      poi=3,knowledge=1,rule=1,source_record=1,source_snapshot=1,import_batch=3
after run1:  poi=3,knowledge=1,rule=1,source_record=1,source_snapshot=1,import_batch=3
after run2:  poi=3,knowledge=1,rule=1,source_record=1,source_snapshot=1,import_batch=3
```

边界：`imports/commit` 本身没有“按业务键 upsert”的幂等实现；直接重复调用 commit 会为
同一 `entry_key/rule_key` 生成新的 `version_no`，并新增 `import_batch`。本次幂等性由脚本
的前置检查保证，未修改 S15 的导入实现。
