## 交付内容

- 规划页可进入 `/wallet`。钱包展示当前账户余额、分页流水、退款金额和有记录的任务编号。管理员可查任意账户及平台流水，并对指定账户申请增减积分报价、复核结果、确认入账。
- 钱包接口扩展 `contracts/openapi/s08-public.yaml`。充值档位由后端定价，调整值由后端校验为有符号整数，报价有效五分钟。确认只接受报价编号及请求去重键。管理员调整额外绑定目标账户版本，确认时重查权限和账户状态。
- 钱包报价、记账和审计使用数据库事务。入账更新余额并追加流水，同一已确认报价只能返回原入账结果。任务确认和失败退款由状态机处理，新退款流水保留任务及报价引用。历史退款继续显示金额。
- 对账默认每小时整点按协调世界时运行，可通过 `app.wallet.reconciliation-cron` 配置。它在同一查询快照中检查余额、流水净额与归属。异常写脱敏告警和审计记录，由运营排查。

## 补充验证（2026-11-24，项目负责人）

本节承接 2026-11-24 发现的 S25 测试隔离限制，实际命令执行于 2026-11-25（Asia/Shanghai）。只改测试与本文，未改积分业务逻辑、契约、迁移或其它步骤实现，也未替任何角色签署“已验证”。

### 修复方式与理由

- 采用“用例开始时记录 baseline”的方案，而不是按本次创建的 user id 过滤：生产对账 `WalletReconciliation.check()` 调用的是整库 `WalletRepository.countUnbalancedAccounts()`；按 user id 过滤需要为测试新增仓储/对账入口，反而绕开生产路径。基线比较让生产方法保持原样，并明确证明本用例制造的新漂移被识别（`baseline → baseline+1`）、撤销后回到 `baseline`。
- 原结尾“再跑一次对账且告警数不变”的断言同样隐含“全库无其它漂移”。库中已存在 S20 合成账号留下的 6 个漂移账户时，生产对账按设计仍会告警，全库计数无法证明“本用例不再告警”。因此该处改为断言全库计数回到 `baseline`、本用例账号余额与流水净额均为 100；同时新增 2 项纯单元测试固定“无漂移不写告警”和“任意漂移账户数只写一条汇总告警”，校验强度不降。
- 账务未变仍按原强度验证：漂移期间余额 101、`GRANT` 流水仍为 1 条；告警仍要求一次对账只新增 1 条审计记录。由于运行库已有 6 个漂移账户，该断言实际覆盖 `baseline+1=7` 个漂移账户，比“仅 1 个漂移账户”更能证明告警是汇总写一次而非按账户逐条写。
