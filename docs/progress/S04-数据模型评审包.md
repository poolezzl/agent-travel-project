## 2. S04 数据模型评审包

### 阶段边界

S04 是 M0 阶段，前置条件为 S01-S03，R5 主责、R8 配合，交付目标是数据模型、数据字典和首版 Flyway。

本阶段允许：

- 冻结 ER、主键、外键、唯一约束、索引、owner 和审计规则；
- 设计账号、行程、任务、来源、POI、知识、规则、积分和审计等数据边界；
- 评审 P1 数据域是否进入首版迁移。

本阶段禁止：

- 实现 Java 业务逻辑；
- 实现 Controller、Service、Repository；
- 实现认证、任务状态机、积分 API、社区 API；
- 直接提交未经 R1/R5/R8 确认的 migration。

依据：`docs/04-逐步开发提示词.md`、`docs/需求追踪矩阵.md`。

### R5/R8 职责边界

- R5：MySQL/Flyway、账号权限、行程持久化、任务、Outbox、来源快照、积分、导出、提醒、审计和公共治理能力。
- R8：社区、榜单、历史、偏好记忆和个人主页聚合的业务规则。
- R5 为社区提供归属校验、敏感词、反刷、下架失效、文件安全和审计等公共能力。
- R8 不负责 Agent 决策、Prompt、路线算法或天气算法。

依据：`docs/roles/05-R5-业务后端与平台能力规范.md`、`docs/roles/08-R8-沉淀层与社区规范.md`。

### ER 关系

- `user_account 1:N user_session`
- `user_account 1:N itinerary`
- `itinerary 1:N itinerary_version`
- `itinerary_version` 通过 `parent_version_id` 自引用，表示版本演进。
- `itinerary_version 1:N itinerary_diff`
- `itinerary_version M:N source_snapshot`，通过 `itinerary_version_source` 关联。
- `planning_task` 归属于用户，可引用行程和基础版本。
- `planning_task 1:N task_step`
- `planning_task 1:N task_event`，唯一键为 `task_id + sequence_no`。
- `task_step 1:N agent_result`，按尝试次数保存结果。
- `agent_result M:N source_snapshot`，通过 `agent_result_source` 关联。
- `planning_task` 与 `outbox_event` 是聚合关系；当前草稿没有外键，需要决定是否保持多态聚合引用。
- `poi 1:N poi_alias`
- `poi 1:N knowledge_entry`
- `knowledge_entry 1:N knowledge_chunk`
- `poi 1:N reservation_rule`
- `user_account 1:1 points_account`
- `points_account 1:N points_ledger`
- `community_content 1:N community_comment`
- `community_content M:N user_account`，通过 `community_interaction` 关联。
- `community_content 1:N community_report`
- `user_account 1:N user_preference`
- `user_account 1:N notification`
- `user_account 1:N export_job`
- `itinerary_version 1:N export_job`
- `user_account 1:N audit_event`

分类建议：

- 不可变：`itinerary_version`、`source_snapshot`、`itinerary_diff`、`task_event`、`agent_result`、`points_ledger`、`audit_event`。
- 追加关系：`itinerary_version_source`、`agent_result_source`。
- 生命周期更新：`user_session`、`planning_task`、`task_step`、`outbox_event`、`notification`、`export_job`。
- 软删除或停用：行程、POI、知识、预约规则、社区内容、偏好。
- 当前 SQL 没有触发器，不能仅凭 DDL 宣称不可变；不可变规则必须由应用层和测试保证。

## 3. 数据字典复核

说明：`NN` 表示非空，`NULL` 表示可空；`PK` 主键，`FK` 外键，`UQ` 唯一约束，`CK` 检查约束，`IDX` 普通索引。以下是当前草稿候选表的评审字典，不代表批准后的最终结构。

| 表 | 字段与类型 | 约束/索引 | owner、审计、保留与更新 | 结论 |
|---|---|---|---|---|
| `user_account` | `id CHAR(36) NN`、`email VARCHAR(320) NN`、`password_hash VARCHAR(255) NN`、`role/status VARCHAR(16) NN`、登录计数、锁定时间、审计时间 | PK；email UQ；role/status CK | 用户自身或 ADMIN；登录、拒绝和高风险操作需审计；私有资料至删除；允许状态更新 | 缺少 username/phone，待决 |
| `user_session` | UUID、`user_id`、`refresh_token_hash CHAR(64)`、issued/expires/revoked/last_seen、metadata JSON | PK；token hash UQ；用户过期 IDX；用户 FK | 用户 owner；刷新令牌最长 30 天；允许吊销和最后访问更新 | 缺 `expires_at > issued_at` CK |
| `itinerary` | UUID、`owner_id`、title、`city_code`、日期、status、current_version_no、deleted_at、时间字段 | PK；owner/更新时间 IDX；日期和状态 CK；owner FK | owner 过滤；私有历史至用户删除；允许草稿状态和软删除 | 官方逻辑名为 `trip`，城市 FK 和当前版本一致性待确认 |
| `itinerary_version` | UUID、行程 ID、父版本 ID、版本号、etag/hash、状态、schema/model/prompt 版本、`plan_json`、`change_set_json`、创建者 | PK；行程+版本号 UQ；etag UQ；父版本 IDX/FK | 已发布版本不可变；回滚只能新建版本；不允许 UPDATE 发布内容 | 组合 JSON 方案和 `plan_snapshot` 边界待决；`(id, content_hash)` 冗余 |
| `itinerary_diff` | UUID、version/parent version、change_type、affected paths JSON、diff JSON、创建时间 | PK；版本 IDX/FK | 追加、不可变；随版本保留 | 缺 change_type CK，原子变更类型待确认 |
| `source_snapshot` | UUID、source type、source record ID、取得/有效时间、新鲜度、估算标记、hash、metadata、脱敏 payload | PK；type+record+hash UQ；新鲜度 IDX | 不可变；不得保存密钥、完整敏感响应或受限原文 | 缺独立 `source_record`，职责混合 |
| `itinerary_version_source` | version ID、snapshot ID、field path、created_at | 复合 PK；双 FK | 追加、不可变；随版本引用保留 | 方向符合 ADR-0004 |
| `planning_task` | UUID、owner、行程/基础版本、task type/status、幂等键、request/input hash、报价/预扣积分、deadline、state version、时间 | PK；owner+idempotency UQ；状态/截止时间 IDX；FK | owner；任务步骤和脱敏模型元数据 90 天；状态允许更新，终态只结算一次 | 缺 `points_quote`；幂等范围待确认 |
| `task_step` | UUID、task、step、status、attempt、租约、输入 hash、结果 ID、开始/完成/审计时间 | PK；task+step+attempt UQ；租约 IDX；task FK | 任务步骤 90 天；租约状态可更新 | `output_result_id` 无 FK；步骤状态集合待 R1/R5 确认 |
| `task_event` | UUID、task、sequence、event type、event JSON、created_at | PK；task+sequence UQ；task FK | 只追加；任务步骤 90 天 | 符合事件追加要求 |
| `outbox_event` | UUID、聚合类型/ID、事件类型、payload、发布状态、次数、available/published、错误、时间 | PK；ID UQ 冗余；发布 IDX；状态 CK | 与任务、积分预扣同事务；发布状态可更新 | 聚合多态 FK、重试和保留策略待确认 |
| `agent_result` | UUID、task/step、attempt、agent/schema/request/trace、状态、result/error/degraded JSON、generated/created | PK；task+step+attempt UQ；request IDX；双 FK | 脱敏模型元数据 90 天；结果追加 | `request_id` 是否 UQ 待确认 |
| `agent_result_source` | result ID、snapshot ID | 复合 PK；双 FK | 追加 | 符合来源关联 |
| `poi` | UUID、city_code、name、category、经纬度、坐标系、状态、snapshot ID、时间 | PK；城市+名称、城市+状态 IDX；状态 CK；source FK | R5 存储，R3/R7 内容；发布/停用；来源可追溯 | 缺 `city`/`poi_snapshot`；坐标检查不足；单 snapshot 不能表达多版本 |

| `knowledge_entry` | UUID、poi、city、title、status、有效期、核验时间、hash、source、creator、时间 | PK；全局 content hash UQ；发布 IDX；多 FK；状态 CK | R3/R7 内容，R5 权限；发布版本不可变，停用/回滚 | 缺版本号/父版本；全局 hash 可能阻碍版本化 |
| `knowledge_chunk` | UUID、knowledge、chunk_no、文本、hash、vector ID、created_at | PK；knowledge+chunk_no UQ；全局 hash UQ；FK | 90 天规则需确认；追加或重建版本 | 缺版本范围 hash 和停用规则 |
| `reservation_rule` | UUID、poi、policy_id、ticket、currency、amount_minor、有效期、timezone、核验、status、source、时间 | PK；policy_id UQ；有效期 IDX；货币金额 CK；FK | 规则超过 30 天 stale；发布版本不可变、停用/回滚 | policy 全局唯一不适合多对象多版本；字段完整性待 R3/R5 |

## 5. V1 草稿审阅结论

逐表结论如下：

- `user_account`：缺 username/phone；账号登录模型不完整。
- `user_session`：基本符合，但缺时间关系检查和清理约束。
- `itinerary`：逻辑命名与官方 `trip` 不一致；缺稳定城市实体及当前版本一致性。
- `itinerary_version`：不可变版本方向正确；JSON/`plan_snapshot` 边界待定；存在冗余唯一键。
- `itinerary_diff`：缺原子 change type 检查。
- `source_snapshot`：包含 `source_record_id` 字段，但没有独立 `source_record`，职责混合。
- `itinerary_version_source`：关联方向符合 ADR-0004。
- `planning_task`：任务状态骨架基本符合；缺独立积分报价生命周期。
- `task_step`：步骤与租约字段基本齐全；`output_result_id` 没有外键。
- `task_event`：`task_id + sequence_no` 追加事件设计符合要求。
- `outbox_event`：事务 Outbox 方向正确；自身 ID 唯一键冗余，多态聚合引用待确认。
- `agent_result`：结构化信封与 JSON 结果方向正确；`request_id` 幂等唯一性待确认。
- `agent_result_source`：来源关联符合契约。
- `poi`：缺 `city`、`poi_snapshot`；坐标和多来源历史不足。
- `poi_alias`：缺停用/软删除状态。
- `knowledge_entry`：缺知识版本和父版本；全局 hash 唯一可能阻碍版本化。
- `knowledge_chunk`：hash 作用域过大；缺版本和停用边界。
- `reservation_rule`：`policy_id` 全局唯一不适合多对象多版本；规则字段和有效期约束仍需内容方确认。
- `points_account`：账户模型基本符合。
- `points_ledger`：追加和业务引用唯一符合；缺余额前后值及 account/user 一致性规则。
- `community_content`：P1 越界风险；只能在 R8/R5 确认后纳入。
- `community_comment`：缺评论父子关系，P1 待 R8 确认。
- `community_interaction`：唯一约束方向合理，但撤销、反刷和奖励幂等未闭合。
- `community_report`：缺举报去重和独立治理案件实体。
- `user_preference`：缺 `preference_evidence`、`preference_summary`；软删除后唯一键阻止重建。
- `notification`：不能覆盖提醒候选、来源规则、时区和候选生命周期。
- `export_job`：缺 `object_metadata`；`LONG_IMAGE` 属 P2，当前纳入范围待确认。
- `audit_event`：追加审计方向正确，但 metadata 脱敏字段集合未约束。

全局问题：

- 当前草稿包含 28 张表，但追踪矩阵还要求冻结 `city`、`poi_snapshot`、`source_record`、`points_quote`、`reminder_candidate`、`post`、`ranking`、`moderation`、`object_metadata`、`preference_evidence`、`preference_summary` 等逻辑域。
- 草稿中的 `plan_json`、`request_json`、`payload_json` 等 JSON 尚未完成“可查询字段列化”边界确认。
- 没有任何机制证明发布版本、来源快照、积分流水和审计事件不可更新。
- 草稿的存在不等于 S04 已实现，也不等于 Flyway 已批准。

## 6. 待 R1/R5/R8 决策的问题

阻断问题：

1. `trip`/`itinerary`、`trip_version`/`itinerary_version`、`plan_snapshot` 的正式物理命名。
2. UUID 使用 `CHAR(36)` 还是 `BINARY(16)`。
3. 计划正文采用 JSON、规范化子表还是组合方案。
4. `source_record` 与 `source_snapshot` 是否拆表。
5. Agent `request_id` 是否必须唯一。
6. `points_quote` 是否进入首版迁移，以及 quote 的状态和过期规则。
7. P1 社区、偏好、导出、提醒是否进入 V1。
8. `city`、`poi_snapshot`、`reminder_candidate` 等逻辑实体的物理表拆分。
9. 社区是否需要 `ranking_entry`、`moderation_case`、评论树和举报去重。
10. 用户删除后的 owner FK、匿名化和审计/积分保留策略。
11. 知识版本、chunk hash、预约规则版本的唯一约束范围。
12. Redis key 的精确格式、版本字段和各域 TTL。
13. 审计 metadata 的最小脱敏字段白名单。
14. `outbox_event` 多态聚合是否保留无 FK 设计。
15. `task_step.output_result_id` 是否建立外键以及如何处理循环依赖。

## 7. 最终结论

当前不允许进入 Flyway migration 实现。

阻断项为：

- 官方要求的若干逻辑实体在草稿中缺失；
- 行程正文与版本快照模型尚未定案；
- 来源记录与来源快照边界未定；
- 积分报价生命周期缺失；
- P1 数据域是否进入首版未完成 R1/R5/R8 决策；
- 用户删除、版本唯一约束、缓存契约和审计脱敏规则未闭合；
- 当前草稿存在命名、约束、索引和边界问题。

因此：

- 不得提交 `V1__initial_s04_schema.sql`；
- 不得将草稿描述为不存在；
- 不得宣称 S04 已完成；
- 不得宣称评审通过；
- 不得自行开始 Flyway 或业务编码。

本轮只读评审完成，等待 R1/R5/R8 评审确认。

## 三、当前可确认的共同约束

以下内容已有官方依据，但不等同于 R1/R8 对具体物理结构的批准：

- MySQL 8、InnoDB、utf8mb4、UTC `DATETIME(6)`。
- Java/Spring Boot 是 MySQL 唯一业务写方。
- Agent 和前端不得直连业务表。
- 已发布行程版本、来源快照、积分流水和审计事件不得被业务更新或物理删除。
- 任务事件按 `task_id + sequence_no` 追加并去重。
- 积分使用整数，流水只追加，业务引用必须支持幂等。
- Redis 队列、缓存、限流必须使用不同前缀，缓存不能作为业务事实来源。
- 审计不得保存密码、Token、完整供应商响应或未经脱敏的个人数据。

依据：ADR-0001、ADR-0002、ADR-0004、ADR-0005、ADR-0006、ADR-0007。
