# 冲突消解与确认规则

| 项目 | 内容 |
|---|---|
| 状态 | Accepted |
| 日期 | 2026-09-20 |
| 执行者 | 总控编排执行，Java 业务后端校验确认命令和版本 |

## 1. 硬约束优先级

冲突按以下顺序裁决：

1. 用户本次显式硬约束：城市/日期、必去点、固定起终点、锁定项和已确认选择。
2. 闭馆、预约、生效期和开放时间。
3. 可达性、交通方式和时间窗。
4. 天气安全与明确风险限制。
5. 用户明确的预算上限。
6. 节奏、主题、口味、评分等软偏好。

高优先级不代表可以违反客观可行性。显式必去点与闭馆冲突时，不得安排闭馆时段，也不得静默删除必去点；必须进入确认态并提供有来源的可选调整。

事实合法性、身份/资源授权、Schema 合法性和来源新鲜度是进入排序前的门禁，不参与偏好权衡，也不能由用户确认绕过。

## 2. 确定性消解

无需确认且不改变保护项时，总控按以下顺序尝试：同日换序、同城同类候选替换、跨日互换、删除最低优先级软偏好项。每次候选都必须重新验证开放时间、可达性、预算和来源。

总控不得：删除必去/锁定项、改变城市或日期、使用过期事实作为硬约束、让直线估算通过路线可行性 Gate、用自然语言掩盖结构化冲突。

## 3. 必须确认的条件

命中任一条件即转 `AWAITING_CONFIRMATION`：

- 删除、替换或改变必去点、用户锁定项、固定起终点。
- 改动已确认预约、已选择票种或跨日安排。
- 所有可行解都会超过明确预算、日期、开放时间或交通硬约束。
- 修改影响范围无法唯一确定，或会波及请求范围以外的日期/Agent。
- 局部修改基于旧版本，需用户在刷新后重新选择。
- 质量校验发现多个可行方案，需要用户在明确代价间选择。

确认请求必须包含：`base_version_id`、冲突代码、受影响日期/对象、保持不变项、可选变更、来源摘要、费用影响和过期时间。具体机器字段由 S02 冻结。

## 4. 不可确认绕过的条件

以下情况直接失败或返回澄清，不提供“仍然继续”：

- 身份、资源归属、余额、幂等键或版本校验失败。
- 必需事实没有合法来源、Schema 无效或模型输出修复后仍无效。
- 路线不可达且没有可验证替代，或安全风险不可接受。
- 用户要求真实支付、代订、抓取受限平台或其他范围外能力。

## 5. 确认生命周期

- 相同 `task_id + confirmation_revision` 只接受一次决定；重复决定返回原结果。
- 接受：以保存的选项和最新 ETag 重新校验；未预扣的确认型局部修改先按服务端报价预扣，再入队。
- 拒绝：转 `CANCELLED`；若存在预扣则幂等退款并转 `REFUNDED`。
- 24 小时无响应：等同拒绝，记录 `CONFIRMATION_TIMEOUT`；不自动选择默认项。
- 确认期间相关行程版本发生变化：返回版本冲突，旧确认失效，不执行或扣费。

## 6. 验收用例

| 用例 | 预期 |
|---|---|
| 必去点闭馆 | 不删除、不安排闭馆时段，给出换日/替换日期选项并等待确认 |
| 普通候选闭馆且有同类候选 | 可确定性替换，保留来源并记录 change set |
| 已确认预约需跨日 | 等待确认，拒绝后原版本不变 |
| 路线只有直线估算 | 标估算，但不能据此宣称硬可行；无精确路线时确认或失败 |
| 预算软偏好超出 | 优先调整软项，不必确认 |
| 明确预算上限无解 | 等待用户提高预算或减少保护项 |
| 重复确认 | 只执行一次、只预扣一次、只创建一个版本 |
| 确认期间版本更新 | 409 冲突，不执行旧选项 |
