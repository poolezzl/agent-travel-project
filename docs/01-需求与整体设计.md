## 一、项目概述

### 1.1 项目背景与核心价值

**背景痛点:**

- 传统攻略获取方式(内容平台搜索、旅行社定制)存在信息碎片化、时效性差、与个人需求错配的问题。用户需要在多个平台之间反复横跳:地图 App 查路线、天气 App 查天气、内容平台查玩法、票务平台查预约规则,最后手工拼装成行程。
- 通用大模型对话式规划(直接问 ChatGPT/通义"帮我规划三天行程")存在幻觉严重、信息过期、缺乏实时数据(天气/路况/预约政策)、无法结构化迭代修改等硬伤。
- 现有商业行程规划产品多为云端 SaaS,定制深度有限,且行程修改往往是"推倒重来"式全量重生成,用户的局部微调诉求得不到满足。

**核心价值:**

1. **信息聚合**:一次输入,多智能体并行拉取路线、天气、玩法、餐饮、预约等多源信息,自动整合为结构化行程。
2. **深度定制**:支持自由文本描述个性化偏好(看日出、摄影优先、少走回头路等),而非固定标签勾选。
3. **可迭代**:自然语言局部修改,"把第二天下午改轻松点"即可定向调整,不破坏其余行程。
4. **可沉淀**:优质行程进入榜单库,UGC 反哺推荐质量,平台价值随使用量增长。
5. **本地可控**:本地部署,数据自持,模型与 API 成本可控,适合团队自建自用与后续演进。

### 1.2 项目定位

**本地部署的多智能体协同文旅规划平台**,面向有定制化出行需求的用户,支持自然语言交互迭代。

- **形态**:B/S 架构 Web 应用,服务端部署在本地服务器/开发机,浏览器访问。
- **用户**:第一阶段面向团队内部及小范围种子用户(自由行深度玩家、摄影爱好者、亲子家庭等有定制诉求的人群);不追求初期大规模并发。
- **模式**:「参数输入 + 自然语言」双通道交互;生成结果结构化呈现,支持对话式迭代。
- **与竞品差异**:不做机酒预订交易闭环(初期),专注"规划智能"这一环做深。

### 1.3 核心目标

实现完整闭环:

```
输入参数 → 智能体协同生成攻略 → 自然语言修改优化 → 路线榜单推荐(沉淀/复用)
```

拆解为四个可验收的子目标:

| # | 子目标 | 顶层验收口径 |
|---|---|---|
| G1 | 结构化行程生成 | 给定城市/时间/必去景点/偏好,产出逐日行程,含路线、时长、交通、天气、餐饮、预约提示,内容真实可用 |
| G2 | 多智能体协同 | 7 类 Agent 按调度流程协作,单次生成端到端耗时 ≤ 3 分钟(流式进度,首屏反馈 ≤ 10 秒) |
| G3 | 自然语言迭代 | 支持局部修改不全量重生成;支持一次产出 2~3 套差异化方案并对比 |
| G4 | 榜单与 UGC | 分类榜单可浏览、可一键复用为个人行程草稿;用户可上传行程与评分 |
| G5 | 历史记录与偏好分析 | 用户可查看/筛选名下全部历史行程;系统对历史记录汇总分析产出偏好画像,并反哺后续生成 |

### 1.4 功能边界(Out of Scope,本期明确不做)

> 边界清晰是 8 人团队不失控的前提。以下内容**本期不做**,列入第八章扩展方向:

- ❌ 机票/火车票/酒店的**在线预订与支付交易**(仅做推荐与跳转外链)
- ❌ 原生 App / 小程序(仅 Web,做移动端自适应)
- ❌ 多人实时协同编辑同一行程
- ❌ 行中实时伴游(定位跟随、实时重规划)——仅做行前规划 + 静态提醒
- ❌ 境外目的地(初期仅覆盖国内城市,地图/天气 API 按国内选型)
- ❌ 对内容平台(小红书等)数据的爬取——**已决策彻底不接**(离线/实时通道均不用),知识库走"人工运营 + 官方公开资料 + UGC"路线,详见 7.3

### 1.5 参考项目分析:TripStar(旅途星辰)

> TripStar 是同定位的开源项目(GPL-2.0,v2.1.0,FastAPI + Vue 3 + HelloAgents 框架),本地副本位于 `D:\TripStar`,可直接运行研读。它已把"输入参数 → 多智能体生成攻略"的**前半段闭环**做到了可用水准,是本项目最重要的参考系。

**已验证、可直接借鉴的能力:**

| 能力 | TripStar 做法 | 对本项目的启示 |
|---|---|---|
| 异步任务 + 进度推送 | `POST /plan` 立即返回 task_id,后台 asyncio 任务,WebSocket/轮询推进度,解决 LLM 长耗时 504 问题 | 与本文 3.4 设计一致,方案已被验证,照此实施 |
| 三路并行采集 | 景点(小红书)/ 天气 / 酒店 `asyncio.gather` 并发,再串行进终极 Planner Prompt | 验证了 3.2 并行 DAG 的可行性与收益 |
| 小红书数据通道 | Cookie + 原生签名直连(失败降级 SSR 抓取)搜游记 → LLM 从长文中提纯景点/时长/避坑/**预约提示**的结构化 JSON;景点实拍图同源搜取 | **已决策不采用**(合规考量,附录 A-Q14):知识库改为人工运营 + 官方公开资料建设,见 7.3 |
| LLM 输出容错 | 大 JSON 返回做五级修复(清杂字符→修引号→补括号→暴力提取→LLM 修补) | 吸收为 LLM 网关标准能力(见 4.1) |
| 双地图引擎 | Google/高德自动回退,统一 geocode 调度层 | 适配层多源切换的现成范式;境外支持(扩展方向)可直接复用 |
| 预算明细面板 | 门票/餐饮/住宿/交通分维度汇总账单 | 吸收为 2.1 输出维度(原稿仅有花费区间,升级为明细) |
| 用户偏好记忆 | 分权重偏好库 + 遗忘机制 + TOP-K 召回,生成后自动提取入库,下次注入 Prompt | 本期 P1 模块(2.5.4),M2 Gate 通过后实施 |
| 伴游 AI 问答 | 行程生成后悬浮问答窗,AI 持有完整行程上下文 | 与交互修正 Agent 合并为"问答 + 修改"一体交互(2.2.7) |
| 知识图谱可视化 | 行程转 ECharts 节点关系图(城市-天-景点-预算) | 前端展示层可选亮点,低成本吸收 |

**TripStar 未覆盖、即本项目的增量价值(评审时对齐"我们凭什么再做一个"):**

1. **迭代闭环缺失**:无自然语言局部修改、无版本管理与回滚、无多方案对比——它的问答只能"问"不能"改",行程不满意只能全量重生成。这正是本项目 G3 目标与交互修正 Agent 的核心价值。
2. **无沉淀层**:无用户体系、无榜单、无 UGC,行程用完即弃,平台无飞轮(本项目 G4)。
3. **规划智能靠 LLM 硬扛**:最终行程由一个大 Planner Prompt 一次性生成完整 JSON,路线顺序、时长、预算均出自 LLM,再用五级容错解析兜底——与本文 2.1 的反幻觉红线相悖。本项目坚持"事实数据来自 API/规则库、动线交给算法"的路线,这是质量上限的根本差异。
4. **预约信息不成体系**:预约提示靠从小红书游记里"提纯",时效与覆盖不可控;本项目以人工核验的预约规则库为准(2.2.6)。
5. **无导出(PDF/ICS)、无提醒、无缓存策略**(它每次生成都实时打 API)。

**复用策略(已决议,附录 A-Q13):**

- **方案 A:基于 TripStar 二次开发** —— M1 起点大幅提前(可运行系统 + 小红书通道 + 地图/天气接入现成),但需接受其技术债(HelloAgents 的字符串协议工具调用较脆弱、无数据库、大 Prompt 架构需重构),且 **GPL-2.0 具有传染性:仅团队内部使用不触发开源义务;一旦对外发布/分发,整个衍生项目必须以 GPL-2.0 开源**。
- **方案 B:自研,借鉴其方案与代码思路** —— 架构按本文档从头搭(LangGraph + 契约化 Schema + 算法层),TripStar 作为活参考与效果基线;独立模块可参考重写。工期较长但无协议约束、无债务。
- ✅ **决议:方案 B 为主体,同时把 TripStar 部署为团队的"效果对照基线"**(每个里程碑与它对比生成质量);其小红书通道**不再复用**(Q14 已决策不接内容平台数据)。

## 二、核心功能需求

> 本章描述功能定义、输入输出与业务逻辑,不涉及实现代码。每个模块给出「功能定义 / 输入 / 输出 / 业务逻辑 / 边界与规则」五段式描述。

### 2.1 自定义行程生成模块(核心模块)

**功能定义**:用户提交结构化参数与自由文本偏好,系统生成逐日详细行程。

**输入维度:**

| 输入项 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 游玩城市及顺序 | 结构化(城市列表,可拖拽排序) | 是 | 支持单城市与多城市串联;多城市时系统校验城市间交通可达性 |
| 起止时间 | 结构化(日期 + 可选每日出发/结束时段) | 是 | 支持"第一天下午到、最后一天中午走"这类半日粒度 |
| 必去景点 | 结构化(景点搜索选择)+ 自由文本兜底 | 否 | 必去景点为硬约束,行程必须包含;冲突时(如闭馆)提示用户 |
| 个性化偏好 | **自由文本** | 否 | 想做的事自由填写:看日出/日落、爬山、摄影、美食优先级、节奏松紧、预算区间、同行人构成(带老人/小孩)、忌口等 |
| 交通偏好 | 结构化(公共交通/自驾/打车/混合) | 否 | 默认混合,影响路线规划 Agent 策略 |
| 方案数量 | 结构化(1~3 套) | 否 | 默认 1 套;选多套时按 2.4 多方案逻辑生成 |

**输出维度(单套方案):**

- **行程总览**:总天数、城市顺序、行程主题概括、节奏评估(紧凑/适中/宽松)、**预算明细面板**(门票/餐饮/住宿/交通分维度汇总,借鉴 TripStar;门票价格来自规则库、交通费来自路线计算,餐饮/住宿为区间估算并标注)。
- **每日详细行程**,每个行程单元包含:
  - 时间节点(到达/游览/离开时刻,精确到半小时粒度)
  - 地点(景点/餐厅/酒店,含坐标)
  - 游览时长建议(结合景点体量与用户节奏偏好)
  - 点位间交通方式、路线、预计通勤时长
  - 当日天气提示(温度区间、降水概率、穿衣/装备建议)及天气不佳时的备选安排
  - 餐饮推荐(午/晚餐,基于当前点位周边)
  - 预约提示(该景点是否需预约、预约渠道、放票时间、免费/票价)
  - 玩法与避坑提示(最佳机位、日出时刻、排队策略等,与用户偏好关联)
- **附加信息**:住宿建议(按每晚落脚点)、跨城交通建议、整体注意事项、景点配图(前端懒加载,来自知识库预置图与 UGC 上传实拍图,不阻塞行程生成)。

**业务逻辑(概要):**

1. 输入校验与解析:总控 Agent 将自由文本偏好解析为结构化偏好标签 + 保留原文;校验时间/城市/必去景点的基本可行性(如 5 个必去景点塞进 1 天,先提示不合理)。
2. 任务拆解与并行调度:按第三章协作流程,分发给各专业 Agent。
3. 汇总与冲突消解:总控 Agent 整合各 Agent 结果,处理冲突(景点周一闭馆→调整到别的日期;下雨→室内方案前置)。
4. 格式化输出:生成结构化行程数据(前端渲染)+ 自然语言摘要。

**边界与规则:**

- 行程数据必须**可溯源**:路线时长来自地图 API、天气来自天气 API、预约规则来自规则库,LLM 只负责组织与决策,**不允许 LLM 凭空生成时长/票价/预约政策等事实性数据**(反幻觉红线,评审重点)。
- 覆盖城市:初期预置北京、上海、杭州、南京、苏州、成都、西安、重庆、广州、厦门 10 城;M1 先完成北京。非预置城市只提供有合法来源的路线和天气能力,知识库未覆盖的景点事实返回未知,不允许使用 LLM 通识补写。

### 2.2 多智能体协作系统

**功能定义**:七类职能 Agent 在总控调度下协同完成行程生成与修改。各 Agent 的定位、输入输出如下(协作机制详见第三章)。

#### 2.2.1 总控调度 Agent(Orchestrator)

- **职责**:需求理解与任务拆解;按依赖关系调度各 Agent(可并行的并行);结果整合与冲突消解;输出格式化;全流程状态管理与失败兜底。
- **输入**:用户完整需求(结构化参数 + 自由文本)/ 修改指令。
- **输出**:最终行程方案(结构化 JSON + 自然语言摘要);对各 Agent 的子任务指令。
- **关键规则**:是唯一与用户对话链路直接对接的 Agent;拥有对子 Agent 结果的最终裁决权;子 Agent 失败/超时时执行降级策略(见 3.5)。

#### 2.2.2 路线规划 Agent

- **职责**:调用地图 API,完成点位间路径计算、游览顺序优化(减少回头路)、通勤时长估算、交通方式推荐。
- **输入**:当日点位集合(含必去约束)、交通偏好、时间窗约束。
- **输出**:排序后的点位序列、逐段路线(方式/时长/距离/换乘概要)、当日总通勤时长。
- **关键规则**:顺序优化本质是带时间窗的 TSP 类问题,由**算法(而非 LLM)**求解,LLM 仅做柔性偏好的加权输入(如"日落时分要在江边"转化为时间窗约束)。

#### 2.2.3 气象服务 Agent

- **职责**:调用天气 API,获取行程日期逐日/逐时段预报;匹配行程时段给出建议;对天气敏感项(日出/日落/爬山/户外摄影)给出可行性判断与备选方案建议。
- **输入**:城市 + 日期区间 + 行程草案中的天气敏感点位。
- **输出**:逐日天气数据、出行建议、"天气不佳时调整建议"(如互换第 2/3 天)。
- **关键规则**:预报周期外(通常 7~15 天以上)的日期,降级输出气候统计参考并明确标注"非预报数据";行程临近时由提醒模块触发复查(见 2.5.2)。

#### 2.2.4 景点资讯 Agent

- **职责**:从本地景点知识库(人工运营 + UGC 沉淀)提取景点玩法、游览建议、避坑提示、热度信息、开放时间。
- **输入**:景点列表 + 用户偏好标签。
- **输出**:每个景点的资讯卡(玩法要点、建议时长、最佳时段、避坑、热度分)。
- **关键规则**:只读本地知识库(预置 + 运营维护 + UGC 沉淀),数据源与更新时间随结果输出;**不接外部内容平台实时数据**(已决策,见 7.3)。

#### 2.2.5 餐饮住宿 Agent

- **职责**:基于行程点位与用餐/入住时点,推荐周边高适配餐饮与住宿。
- **输入**:行程草案(点位 + 时间)、口味偏好/忌口、预算区间、同行人构成。
- **输出**:每餐 2~3 个候选(名称、位置、人均、招牌、与前后行程点的距离)、每晚住宿区域建议 + 候选。
- **关键规则**:推荐半径与"顺路性"优先于绝对评分(不为一顿饭绕路 40 分钟);仅推荐 + 外链,不做预订。

#### 2.2.6 预约规则 Agent

- **职责**:维护景点预约政策库(是否需预约、渠道、放票时间、提前天数、票价、免票政策),为行程注入预约提示,并生成提醒任务(交给提醒模块执行)。
- **输入**:行程中的景点列表 + 游玩日期。
- **输出**:每景点预约信息卡;预约时间线(哪天几点该抢哪个票)。
- **关键规则**:预约政策为**人工/半自动维护的规则库**,不由 LLM 生成;每条规则带"最后核验时间",超过时效阈值(30 天)时输出并提示"请以官方渠道为准"。

#### 2.2.7 交互修正 Agent

- **职责**:理解用户自然语言修改意见,定位受影响的行程范围(单点/单日/跨日),生成最小修改方案;维护方案版本,支持多版本对比;兼任**伴游问答**(见下)。
- **输入**:当前行程版本 + 用户修改指令(如"第二天太累了,砍掉一个景点"、"把美术馆换成适合带孩子的地方")或询问指令。
- **输出**:修改影响范围说明 → 局部重规划指令(回给总控,仅调度受影响的 Agent)→ 新版本行程 + 变更摘要(diff 视图);问答场景直接输出答案。
- **关键规则**:遵循**最小改动原则**;修改若波及必去景点或引发连锁冲突,先向用户确认再执行;版本保留上限 10 个/行程。
- **问答/修改一体**(相对 TripStar 的增强):TripStar 已验证"持有完整行程上下文的悬浮问答窗"体验价值,但其问答只能答不能改。本项目统一入口:Agent 先做意图分类——**询问**(直接基于行程上下文与知识库回答,如"故宫票价多少")或**修改**(走上述修改链路),用户无需区分两种模式。

### 2.3 行程迭代优化模块

**功能定义**:围绕已生成行程的持续对话式优化。

**2.3.1 自然语言局部修改**

- 支持粒度:单个景点(换/删/增)、单日(节奏调整、整日重排)、跨日(两天互换)、全局参数(整体换酒店档次)。
- 业务逻辑:修改指令 → 交互修正 Agent 判定影响范围 → 总控只重调度受影响 Agent → 合并回主行程 → 生成变更摘要供用户确认。
- **不全量重生成**是硬性要求:未受影响的日期/点位数据保持原样(用户可能已对其形成心理预期)。
- 用户可对修改结果"撤销/回滚到任意历史版本"。

**2.3.2 多方案生成**

- 一次生成 2~3 套差异化方案,差异化维度:
  - **节奏松紧**:紧凑打卡型 vs 深度休闲型
  - **路线结构**:不同的城市内动线/景点组合(必去景点在所有方案中均保留)
  - **预算档位**:经济型 vs 舒适型(已决议纳入,附录 A-Q8;主要体现在餐饮/住宿候选的档位过滤与门票可选项取舍)
- 输出对比视图:各方案的天数节奏、总通勤时长、覆盖景点数、预估花费并列对比;用户选定一套后进入迭代,其余方案保留可切换。
- 成本控制:多方案共享同一批 Agent 原始数据(天气/资讯/规则只查一次),仅路线与编排层差异化;预算档差异仅重查餐饮/住宿候选(按档位过滤),避免 API 与 token 成本翻倍。

### 2.4 路线推荐榜单与社区系统

**功能定义**:优质行程的沉淀、排序与分发,形成"生成→沉淀→复用"飞轮;同时承载用户分享行程、互动交流的社区能力——**社区与榜单是同一套内容的两个视图,不是两套体系**:社区动态流是全量视图,榜单是达标/精选子集(已决议,附录 A-Q20)。

**推荐算法维度**(初版为加权评分制,不上重型推荐模型):

| 维度 | 说明 | 数据来源 |
|---|---|---|
| 热度 | 浏览/复用/收藏次数 | 平台行为数据 |
| 评分 | 用户显式打分(1~5 星)+ 评价 | UGC |
| 季节适配 | 行程与当前/目标季节的匹配度(赏花/滑雪/避暑) | 景点标签 + 规则 |
| 行程合理性 | 系统评估:通勤占比、节奏均衡度、开放时间冲突数 | 平台算法 |
| 人流量 | 景点拥挤度(节假日权重) | 初期用"节假日 + 热度"规则近似;M1 后评估是否采购百度慧眼等商业数据源 |

**分类榜单:**

- 按城市:城市 Top 行程榜
- 按主题:亲子 / 徒步 / 摄影 / 美食 /(可扩展标签体系)
- 按天数:周末 2 日 / 3~4 日 / 一周深度
- 组合筛选:如"北京 · 亲子 · 3 日"

**UGC 能力:**

- 用户可将自己的行程(平台生成后实际走过的,或手工编辑的)发布到榜单库,附游记式点评与实拍图。
- 其他用户可对榜单行程打分、评价、"一键复用"(拷贝为自己的草稿,再走迭代优化流程改成自己的版本)。
- 内容治理:发布时敏感词过滤,上榜后人工抽审,配合举报下架机制(已决议,附录 A-Q7);低质/违规内容下架。管理员(2.6)是内容治理的执行主体:承接审核队列、举报工单与榜单人工干预(置顶/下架/排序修正)。

**社区动态流(本期新增,合并入本模块,已决议,附录 A-Q20):**

- **定位**:全量视图。用户发布的每篇行程游记/点评默认进入社区动态流(按最新/最热切换排序),**先发后审**——敏感词过滤实时拦截,人工抽审事后补充治理,不做"审核通过才可见",避免打击分享积极性。
- **榜单是动态流的精选子集**:满足上述推荐算法五维度加权分达标,或经管理员人工挑选,才进入分类榜单;二者共用同一套内容、评论、点赞、举报数据,不重复建两套内容与治理规则。
- **互动能力**:点赞、评论(评论同样走敏感词过滤)、收藏、一键复用(与榜单共用)。
- **积分激励(可选亮点,不占关键路径)**:行程被复用或进入榜单时,发布者获得少量积分奖励(计入 2.7 钱包体系),强化"生成→分享→积分→再生成"的飞轮,呼应 G4"UGC 反哺推荐质量"目标。

### 2.5 辅助功能模块

**2.5.1 行程导出**

- **PDF**:排版友好的行程手册(逐日行程 + 地图缩略 + 预约清单),可打印。
- **ICS 日历**:行程单元转日历事件(含地点/提醒),可导入手机日历。
- **图片长图**:单页长图,适合发社交平台/群聊分享。

**2.5.2 提醒功能**

- 景点预约截止提醒:按预约规则 Agent 生成的预约时间线,提前 1 天 + 1 小时两档提醒。
- 天气变化预警:行程临近(进入预报有效期)后自动复查天气,与生成时结论显著不符时推送预警及调整建议。
- 路况提醒:出行日早间推送关键路段/管制信息(初期降级为仅节假日拥堵常识提示,实时路况列为后续增强)。
- 提醒通道:**仅站内消息**(已决议,附录 A-Q6);邮件/微信 webhook 列为后续增强,不在本期范围。

**2.5.3 本地数据缓存**

- 缓存对象:常用城市的景点库、POI 基础信息、历史路线计算结果、天气数据(短 TTL)、景点资讯卡。
- 目标:减少第三方 API 调用量(配额与费用)、降低生成延迟、支持 API 短暂不可用时的降级服务。
- 策略要点:不同数据类型不同 TTL(天气按小时、路线按周、景点基础信息按月、预约规则按人工核验);缓存命中与数据新鲜度需对用户透明(展示"数据更新于 X")。

**2.5.4 用户偏好记忆(本期纳入,机制借鉴 TripStar)**

- TripStar 已实现分权重偏好库 + 遗忘机制 + TOP-K 召回:行程生成成功后自动提取稳定偏好(节奏/口味/预算档)打分入库,下次规划时将高权重偏好注入 Agent 上下文,推荐随使用越来越贴合。
- 原稿列为 M3 可选项;因 2.5.5 历史偏好分析已确定纳入本期且依赖同一偏好库,本模块**升级为本期正式范围**(M3 交付),机制参考 TripStar 重新实现。
- 边界:偏好注入仅作为软性权重,不得覆盖用户当次显式输入;偏好数据本地存储,用户可查看与清空。

**2.5.5 历史行程记录与偏好分析(本期新增)**

- **功能定义**:用户可查看名下全部历史行程记录,并由系统对记录汇总分析,产出个人偏好画像。
- **历史记录查看**:
  - 记录范围:平台生成的行程(含各历史版本)、复用榜单后修改的行程、手工编辑的行程;
  - 列表能力:按时间/城市/天数/状态(草稿、已定稿、已出行、已上榜)筛选与搜索;支持从任意历史行程"再来一单"(拷贝为新草稿进入迭代流程)、对比同一行程的版本演进;
  - 数据来源:行程库 + 版本库 + 行为数据(复用/收藏/评分),无需新增采集。
- **偏好汇总分析**:
  - 分析维度:常去城市/目的地类型分布、主题偏好(亲子/摄影/徒步/美食)、节奏松紧倾向、预算档分布、出行频率与季节习惯、常见修改模式(如"总是砍掉早起项"→ 晚起型);
  - 呈现:个人主页偏好面板(图表可视化)+ LLM 生成的一段自然语言"出行画像"解读;
  - 反哺:分析结论写入 2.5.4 偏好记忆库(带权重),作为后续行程生成的软性输入;
  - 实现口径:统计维度用**规则聚合**(SQL/离线任务),LLM 仅做画像文案表达——延续"事实靠数据、表达靠 LLM"的反幻觉原则;历史行程数少于 3 条时不出画像(样本不足,避免过拟合尬猜)。
- **边界与规则**:偏好画像仅用户本人可见;可一键清空分析结果与偏好库;画像不参与榜单排序等公共场景。

**2.5.6 个人主页(本期新增)**

- **定位**:个人主页是**聚合入口**,不是新的数据模型——把散落在各模块的"我的数据"串成一个页面,包括:
  - 历史行程记录与偏好画像面板(2.5.5)
  - 偏好记忆库查看/清空入口(2.5.4)
  - 钱包:余额、充值、消费/退款流水(2.7)
  - 我的社区内容:我发布的行程、收到的点赞与评论(2.4)
  - 账户设置:资料、密码修改(2.6)
- **边界与规则**:个人主页仅展示与操作当前登录用户自己的数据;各子项的数据来源、权限与边界均以其归属章节(2.4/2.5.4/2.5.5/2.6/2.7)为准,本节不重复定义。

### 2.6 账号与权限体系(本期新增)

**功能定义**:提供登录鉴权与角色区分,支撑全平台"谁能做什么"的边界。

**输入**:用户名/手机号 + 密码(注册、登录);用户资料与密码修改请求。

**输出**:登录态凭证(会话身份);对普通用户/管理员的功能可见性与操作权限区分。

**业务逻辑(概要):**

- **角色**:仅两级——**普通用户(USER)**、**管理员(ADMIN)**,不做多级 RBAC(团队规模与产品阶段不需要更细的分级)。
- **登录方式**:用户名或手机号 + 密码;预留短信验证码登录位,列为后续增强,不占本期关键路径。
- **未登录可访问范围**:榜单/社区动态流浏览、行程详情只读;生成行程、发布/点赞/评论、个人主页、钱包操作均需登录——降低未登录用户白嫖生成配额的风险,与 1.4"面向种子用户"的定位一致。
- **管理员权限范围**(4 项,均承接文档已有但此前未写明执行主体的动作):
  1. **内容治理**:UGC/社区帖子审核队列、举报工单处理、榜单人工干预(置顶/下架/排序修正)——落实 2.4 已有的 Q7 决议。
  2. **用户管理**:查看用户列表、封禁/解封、重置密码。
  3. **财务管理**:充值/消费/退款流水查询,异常工单核对(见 2.7)。
  4. **运营支持**:知识库/预约规则库的人工核验入口(承接 7.3 已提到的"R7 运营工具",管理员后台是其载体之一,不是新增职能)。

**边界与规则**:管理员账号**内部手工指定**,不做自助申请/审批流程(内部+种子用户阶段人数极少,走开发/运维配置即可,避免过度设计,已决议,附录 A-Q17)。

### 2.7 钱包与计费体系(本期新增)

**功能定义**:以虚拟积分为计量单位的模拟充值与生成扣费体系,让"生成"这一核心动作有成本意识,同时不涉及真实支付合规问题。

**输入**:充值请求(选择档位);生成任务提交(触发预扣)。

**输出**:账户余额;充值/消费/退款流水记录。

**业务逻辑(概要):**

- **计价单位**:虚拟积分(已决议,附录 A-Q18)——积分为平台内部虚拟计量单位,**不可提现、不对应法定货币价值**,与 1.4"不做交易闭环"的边界表述一致。
- **模拟充值**:用户在个人主页钱包页选择充值档位,点击后直接到账,不接入真实支付网关;后续接入微信支付/支付宝列入第八章"后续扩展方向"。
- **计费对象与定价**(已决议,附录 A-Q19):按"一次生成任务"计费,依 2.3.2 已有的方案数量(1~3 套)差异化定价——套数越多扣费越高,因为 Agent 调用量与 token 成本随之线性增加,这是当前唯一有真实成本关联的计费依据。**局部修改(2.3.1)不额外收费或按更低固定值收费**,与文档"不全量重生成即是最大成本节约"的既有卖点保持一致,不自相矛盾。
- **扣费时机**:提交生成任务时**预扣**;任务全链路失败(3.5)时**自动全额退款**。
- **余额不足**:阻止提交生成任务,前端提示"积分不足,请充值",不做透支/欠费。
- **新用户初始积分**:注册赠送 100 体验积分;1/2/3 套方案分别预扣 10/18/25 积分,已确认的局部重规划 2 积分,问答、澄清和失败不收费。

**边界与规则**:每笔充值/消费/退款均生成一条流水记录,用户与管理员可查(用户查自己的,管理员查全平台),延续文档"数据真实性/可观测"的既有原则。

### 2.8 非功能性需求(顶层口径)

| 类别 | 口径(定稿) |
|---|---|
| 性能 | 单次完整生成 ≤ 3 分钟(流式输出进度,首屏反馈 ≤ 10 秒);局部修改 ≤ 1 分钟 |
| 并发 | 初期支撑 10~20 并发生成任务(内部+种子用户规模) |
| 可用性 | 非 7×24 强保障;第三方 API 故障时有明确降级提示,不静默出错 |
| 数据真实性 | 事实性字段(时长/票价/政策)100% 来自 API/规则库,LLM 生成内容明确标注 |
| 安全合规 | 用户数据本地存储;数据源获取方式合规(见 7.3);UGC 内容审核;登录凭证与密码加密存储,积分不可提现、不对应法定货币价值(见 2.7) |
| 可观测 | Agent 调用链路全程留痕(每次生成可回放各 Agent 的输入输出),便于调试与坏案例分析 |

```
      │        不可行(时间/景点冲突)→ 直接返回用户澄清
      ▼
[3] 总控:任务拆解,生成子任务 DAG
      │
[4] ══ 并行阶段一(彼此无依赖)══
      ├─ 景点资讯 Agent:必去景点 + 候选景点资讯拉取
      ├─ 气象服务 Agent:目的地逐日天气
      └─ 预约规则 Agent:相关景点预约政策
      ▼
[5] 总控:初排框架 —— 基于资讯(建议时长/开放时间)、天气(户外项排期)、
    预约(可约日期)约束,决定"哪天去哪几个点"的日级分配
      ▼
[6] 路线规划 Agent:逐日执行点位顺序优化 + 路径/通勤计算(各日可并行)
      ▼
[7] 餐饮住宿 Agent:基于确定的动线,注入每餐与每晚住宿推荐
      ▼
[8] 总控:整合 + 冲突消解(闭馆/超时/天气冲突的最终裁决)
      │        存在硬冲突无法自动消解 → 携选项询问用户
      ▼
[9] 总控:格式化输出(结构化 JSON + 摘要),落库为版本 V1,推送前端
```

多方案模式:步骤 [5] 分叉出 2~3 个编排策略,[6][7] 各自执行,[4] 的数据全程共享。

### 3.3 修改链路(迭代优化)

```
[1] 用户下达修改指令("第二天别安排爬山了,想去博物馆")
      ▼
[2] 交互修正 Agent:意图解析 → 影响范围判定(第 2 天;可能波及第 3 天顺路点)
      │        意图不明确 → 反问澄清;波及必去景点 → 先确认
      ▼
[3] 总控:生成局部重规划子任务(仅第 2 天:资讯→重排→路线→餐饮)
      ▼
[4] 受影响 Agent 执行;未受影响的日期数据原样保留
      ▼
[5] 总控整合 → 新版本 V(n+1) + 变更摘要(diff)→ 用户确认/继续修改/回滚
```

### 3.4 任务流转与通信机制

- **编排模式**:采用**中心化编排(Orchestrator-Worker)**,总控持有全局状态,子 Agent 无状态、不互相直接通信。理由:链路可控、可调试、可回放,远优于去中心化自由对话式协作(后者延迟与不确定性对本场景是纯负担)。
- **通信格式**:Agent 间消息为**结构化 JSON 契约**(每类 Agent 定义清晰的输入/输出 Schema),自然语言仅出现在面向用户的表达层。Schema 即团队内的接口协议,是并行开发的对齐基础(详细 Schema 在下阶段文档定义)。
- **状态管理**:每次生成任务是一个带状态机的会话(排队→解析→并行采集→编排→路线→整合→完成/失败),状态与各步骤中间产物落库,支持断点续跑与全链路回放。
- **执行形态**:异步任务 + 流式进度推送(前端实时看到"正在查询天气…路线规划中…"),避免长时间白屏等待。

### 3.5 失败与降级策略(顶层原则)

| 场景 | 策略 |
|---|---|
| 单个 Agent 超时/失败 | 重试 1 次 → 仍失败则降级:该维度信息缺省并明确标注(如"天气服务暂不可用,建议出行前自查"),不阻塞整体行程产出 |
| 地图 API 失败 | 路线为行程骨架,降级空间小:优先读缓存;无缓存则给出直线距离估算并显著标注"估算值" |
| LLM 输出不合 Schema | 校验 + 自动重试(带错误反馈);连续失败转人工可见的失败态 |
| 全链路失败 | 任务失败对用户可见、可一键重试,保留已采集数据避免重复 API 消耗;预扣积分原路全额退回(见 2.7) |

## 四、技术栈选型建议

> 选型原则:① 适配本地部署;② 8 人团队上手成本与开发效率优先;③ 生态成熟、资料充足;④ 各层选型已在评审中确认,本文为定稿表述。

### 4.1 大模型层

- **决议(附录 A-Q3)**:**M1 使用配置化 OpenAI 兼容云端 API,本地模型属于 P2**。供应商、Base URL、模型名和预算由部署配置注入,真实联调前按 `02-开发决策基线.md` 的外部账号 Gate 验证;P0/P1 不依赖 Ollama。
- **理由**:统一 LLM 网关按任务路由、模型可插拔,先云后混合把"本地模型效果不足"(7.2)的风险从 M1 关键路径上摘掉,同时保留"本地可控"的演进空间。
- **备选**:vLLM 本地推理(有 GPU 服务器时替代 Ollama,吞吐更好)。
- **LLM 网关标准能力**(吸收 TripStar 经验):统一 OpenAI 兼容协议接入、按任务路由模型、Schema 校验 + **多级 JSON 容错修复**(清杂字符→修引号→补括号→提取→LLM 修补,TripStar 五级修复已验证必要性)、失败重试与调用留痕。

### 4.2 智能体框架层

- **推荐**:**LangGraph**(Python)。理由:图式编排与 3.4 的中心化 DAG 模型天然吻合;状态持久化、断点续跑、人工介入(human-in-the-loop)开箱即用;生态与文档最成熟。
- **关于 HelloAgents(TripStar 所用框架)**:轻量易上手,TripStar 用其 SimpleAgent 验证了多 Agent 分工可行;但其工具调用走**提示词字符串协议**(`[TOOL_CALL:xxx:...]`,靠 Prompt 强约束模型原样输出),对模型格式服从度依赖高、易碎,且无状态持久化/断点续跑——TripStar 的天气/酒店 Agent 提示词中大量"必须""不要带多余字符"式防御性措辞即为佐证。本项目的迭代修改、版本管理、失败降级需求(3.3/3.5)需要真正的状态机支撑,故**不推荐沿用**,若走二开路线(1.5 方案 A)也建议将编排层替换为 LangGraph。
- **备选**:自研轻量编排(仅需 DAG + 状态机,依赖最少,但可观测等基建全要自建);CrewAI/AutoGen(更适合自由协作型多 Agent,与本项目强控制流需求不匹配,不推荐)。

### 4.3 后端服务层

- **决议(附录 A-Q4)**:**Java Spring Boot(业务后端)+ Python FastAPI(Agent 编排服务)双栈**。团队 Java 储备显著更强,业务侧(用户/行程/版本/榜单/历史/导出/提醒,R5/R8 负责)用 Spring Boot 开发效率与质量更有保障;Agent 编排、LLM 网关与算法层(R1~R4 负责)留在 Python 生态(LangGraph/LLM 库均为 Python 原生)。
- **跨栈约定**(双栈的代价管理,呼应 7.7):两栈之间以 REST/OpenAPI 契约对接——业务侧提交生成/修改任务给 Agent 服务,Agent 服务回写结果与进度;该契约与 Agent Schema **同批在 M0 冻结**。MySQL 由业务侧统一读写,Agent 服务经 API 存取业务数据(避免双栈直连同库的隐性耦合);Redis 为共享设施(任务队列、进度、缓存)。
- 任务队列:MySQL 任务表为事实来源,事务 Outbox 发布到 Redis Streams Consumer Group;进度统一使用 SSE,命令使用 REST,事件持久化并支持 sequence_no 补拉。
- **登录鉴权(本期新增,2.6)**:**Spring Security + JWT**,角色仅 USER/ADMIN 两级,与团队已定的 Spring Boot 技术栈天然契合,不引入额外框架;JWT 无状态特性也便于与 SSE 长连接场景配合。

### 4.4 前端交互层

- **选定**:**Vue 3 + Vite + TypeScript + Pinia + Vue Router + Element Plus**;地图渲染用高德 JS SDK;行程时间轴、方案对比和 diff 为自研组件。ECharts 知识图谱属于 P2。
- **理由**:Vue 国内生态与团队常见技能匹配度高;SSE 流式渲染成熟;**Vue 3 + 高德 JS API 组合已被 TripStar 验证**(注意高德需三类凭证:后端 Web 服务 Key、前端 JS API Key、JS 安全密钥 JSCode,配置方式参考其 README)。
- **备选**:React + Antd(团队 React 更熟则换,无本质差异)。

### 4.5 数据存储层

- **推荐**:
  - 业务库:**MySQL 8**(用户/行程/版本/榜单/规则库;**本期新增**:用户账号表、钱包账户表、积分流水表、社区帖子/点赞/评论表,详细字段在下阶段文档定义)
  - 缓存:**Redis**(API 结果缓存、任务队列、会话)
  - 向量库:**Chroma 持久化模式**,由单一 Agent 服务拥有,承载景点知识库语义检索(RAG)
  - 对象存储:本地磁盘目录起步(导出文件、UGC 图片),预留 MinIO 升级位
- **理由**:全部组件均可单机本地部署、运维极轻;团队已有 MySQL 经验可复用。

### 4.6 第三方 API 层

| 用途 | 推荐 | 备选 | 备注 |
|---|---|---|---|
| 地图/路径/POI | 高德开放平台 | 百度地图;Google Maps(境外,远期) | 国内数据质量与免费配额均衡;统一封装适配层,保留换源能力(TripStar 的 map_dispatcher 双引擎自动回退可参考) |
| 天气 | 和风天气 | 高德天气(与地图同 Key,免费但仅 3~4 天预报,TripStar 所用)/ 彩云 | 和风支持逐小时与 7~15 天预报,更匹配行程规划需求;高德天气作降级备源 |
| 内容/资讯 | 本地知识库(人工运营 + 官方公开资料)+ UGC 沉淀 | — | 已决议不接小红书等内容平台抓取通道(附录 A-Q14),数据策略见 7.3 |
| 人流量/拥挤度 | 初期用"节假日规则 + 热度"近似 | 百度慧眼等商业数据 | 商业数据源费用高,初期不采购 |

- 统一原则:所有第三方调用走**适配层**(限流、配额监控、缓存、Mock 开关、多源切换),任何 Agent 不直连外部 API。

### 4.7 算法层

- 路径与顺序优化:**OR-Tools**(TSP/VRP 带时间窗)或自实现启发式(点位数少,贪心+2-opt 足够);先自实现简版,复杂度上来再引 OR-Tools。
- 榜单推荐:加权评分公式(2.4 五维度)+ 时间衰减,规则可配置;不上机器学习模型。
- 行程合理性评估:规则化打分(通勤占比、节奏方差、冲突计数),同时服务于生成质量自检与榜单排序。
- 语义检索:Embedding(本地 bge 系列模型)+ 向量库,服务景点知识库 RAG。

### 4.8 部署层

- **决议(附录 A-Q9)**:**裸机脚本部署**(systemd/启动脚本统一拉起 MySQL、Redis、Java 业务后端、Python Agent 服务、前端静态站与 Ollama<若 M2 引入>)。部署目标机无虚拟化条件(装不了 Docker),所有组件均支持裸机运行,此为完整可行路径而非降级;建议提供一键启动/停止脚本与端口/进程清单文档。
- **备选**:Docker Compose 单机编排——若后续更换支持虚拟化的服务器可平滑迁移。
- 基础可观测:结构化日志 + Agent 链路留痕落库;初期不上 Prometheus 全家桶。

## 七、风险与应对思路

### 7.1 第三方 API 调用限制与成本

- **风险**:地图/天气免费配额有限,生成一次行程 API 调用密集;超配额导致服务不可用或费用失控。
- **应对方向**:适配层统一限流与配额监控告警;多级缓存最大化复用(路线结果按点对缓存);批量接口优先;多方案共享数据;必要时多 Key/多源轮换(在服务条款允许范围内);为核心 API 预留小额付费预算。

### 7.2 本地模型效果不足

- **风险**:本地开源模型在复杂任务拆解、长上下文整合、严格 JSON 输出上不稳定 → 行程质量差或链路频繁失败。
- **应对方向**:混合模型策略(关键环节走云 API);把"智能"尽量从 LLM 移到规则与算法(LLM 只做理解与表达,计算交给算法层);Schema 校验 + 自动纠错重试;建立生成质量评估集,模型选型用数据说话;Prompt 与案例库持续沉淀。

### 7.3 内容数据源策略(已决议:不接内容平台抓取通道)

- **决议(附录 A-Q14)**:**彻底不使用**小红书等内容平台的抓取通道——离线批量拉取与线上实时通道均不用,从根源规避 Cookie 失效/封号、签名接口随版本失效的维护成本,以及平台条款与合规层面的法律风险。TripStar 的该模块仅作为"游记→LLM 提纯"内容形态的产品参考,不复用其实现。
- **替代数据策略(三条腿):**
  1. **人工运营建库为主**:R7 主责首批 10 城的知识库建设,数据来源为**官方公开渠道**(景区官网/官方公众号的开放时间、票价、预约政策)+ 团队实地经验与公开攻略资料的人工整理;R3 提供录入/核验运营工具降低边际成本;M0 的 TripStar 体验报告用于提炼"资讯卡该长什么样"的内容模板。
  2. **无事实兜底**:知识库未覆盖的城市/景点只返回有来源的路线和天气;LLM 可输出明确标记的非事实性表达建议,但不得补写景点、时长、开放时间、票价、预约或餐住事实。
  3. **UGC 沉淀反哺**:榜单、评分、游记点评与实拍图持续充实知识库,是长期的内容供给主力(G4/G5 飞轮)。
- **残余风险与对策**:初期知识库在"玩法/避坑"深度上弱于真实游记提纯路线,行程攻略味较淡——通过内容模板化、每周质量评审会补内容短板、UGC 增长逐步弥补;人工建库工作量集中在 R7,数据建设高峰期(M0~M2)由 R3/R8 支援录入。

### 7.4 路径与行程合理性

- **风险**:LLM 编排的行程出现"上午颐和园下午天坛再回香山"式的反人类动线,或时长估算失真,直接摧毁产品可信度。
- **应对方向**:动线交给算法(TSP + 时间窗)硬约束;游览时长以知识库数据为准;行程合理性规则化打分,低分方案在输出前自动重排;质量评审会持续收集坏案例回归。

### 7.5 多 Agent 链路延迟与 token 成本

- **风险**:串行调用叠加导致生成耗时数分钟以上;每次生成 token 消耗大。
- **应对方向**:最大化并行(3.2 的 DAG 设计);流式进度反馈管理用户预期;分模型路由(简单任务小模型);中间产物缓存;局部修改机制本身就是最大的成本节约(避免全量重生成)。

### 7.6 数据时效性

- **风险**:预约政策、开放时间、票价变动频繁,过期信息误导用户实际出行。
- **应对方向**:所有事实数据带"核验时间"并对用户展示;超阈值自动标注"请以官方为准";提醒模块在行程临近时触发关键信息复查;建立轻量的人工核验运营流程(R7)。

### 7.7 团队并行与集成风险

- **风险**:8 人并行开发 Agent,契约不清导致集成期大面积返工。
- **应对方向**:Schema 契约先行并冻结(变更走评审);适配层提供 Mock 数据源使各 Agent 可独立开发测试;M1 尽早端到端集成,不留到后期"大爆炸式联调";统一的 Agent 链路留痕便于定位问题归属。

## 八、后续扩展方向

按价值与可行性排序,均不在本期范围:

1. **行中模式**:出行中实时定位 + 动态重排(景点排队超预期→自动调整后续安排),从"行前工具"升级为"全程伴游"。
2. **多端形态**:微信小程序 / App,行中场景的自然载体。
3. **多人协同**:结伴出行的行程共编、偏好合并(A 要摄影 B 要美食的折中方案)。
4. **预订闭环**:机酒/门票比价与预订跳转分佣,商业化路径。
5. **语音交互**:行中免手动的语音改行程。
6. **境外目的地**:地图/天气/内容源全面换源,支持出境游(TripStar 的 Google/高德双引擎调度与代理配置方案可直接复用)。
7. **Agent 能力开放**:各 Agent 封装为标准工具(MCP 等协议),供外部智能体生态调用,平台从应用升级为能力底座。
8. **多语言国际化**:界面 + LLM 输出 + 数据层的多语言适配(TripStar 已有中/英/日完整方案可参考)。
9. **社区化运营**:达人认证、行程专栏、话题活动,在本期社区动态流(见 2.4)基础上做进一步深化。
10. **真实支付网关接入**:钱包充值由本期"模拟充值"(2.7,虚拟积分不可提现)升级为接入微信支付/支付宝等真实支付渠道,届时需补支付合规与资质评估。

> 注:原第 8 项"个性化画像"已纳入本期 P1(见 2.5.4),不再列于后续扩展。
