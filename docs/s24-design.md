# S24 技术说明：历史行程、偏好分析与偏好记忆

## 模块定位

S24 是多智能体协作文旅规划平台的第 24 个开发步骤，由 R8 承担。平台为用户生成的行程在步骤结束后一般不保留结构化记录，后续规划无法复用历史信息，用户每次都需要重新说明自己的旅行偏好。S24 让平台越用越懂用户：系统将行程累积为历史数据，从中统计用户偏好，并将结果用于后续行程生成。

对应需求 2.5.4、2.5.5，目标 G5，算法 ALG-12。

偏好统计须基于规则从真实历史数据计算，语言模型仅负责将统计结果改写为自然语言，不参与数值生成。该约束用于避免模型编造偏好，保证结果可追溯。

## 功能构成

### 历史行程

用户生成的行程存入 `trip` 与 `trip_version` 表。S24 提供按时间、城市、天数、状态（DRAFT、ACTIVE、ARCHIVED）筛选及标题检索的能力，检索限定在当前用户范围内。"再来一单"将选中行程复制为新的草稿，复制过程中移除私密偏好字段与精确住宿地址，以降低敏感信息扩散风险。

版本演进对比读取同一行程的两个 `plan_snapshot` 快照，递归摊平成"字段路径到值"的映射后按路径求差，输出新增、删除、修改三类变化。字段路径用点号加数组下标表示，例如 `days[0].spots`。调用方可指定起止版本 ID，省略时取最早与最新版本。数据只来自 `trip_version` 与 `plan_snapshot`，不新增采集；归属校验在查询 SQL 中关联 `trip.owner_id`，只返回本人行程的版本。差异条数上限为 200，避免快照过大时响应膨胀。

### 偏好画像

对历史行程进行统计，产出五个维度，全部由规则聚合，不含模型推断：

| 维度     | 含义    | 数据来源                                                                 |
| ------ | ----- | -------------------------------------------------------------------- |
| city   | 常去的城市 | `trip_city` 关联 `city`，按出现次数排序                                       |
| theme  | 偏好的主题 | `plan_snapshot.plan_json` 的 `trip.preferences` 标签，按出现次数统计              |
| pace   | 节奏松紧  | `plan_json` 的 `summary.point_count` 除以 `trip.day_count`，分轻松/适中/紧凑       |
| budget | 预算档位  | `plan_json` 的 `trip.budget.amount_minor`（单位分），分经济/舒适/高端             |
| season | 出行季节  | `trip.start_date` 的月份，分春/夏/秋/冬                                     |

统计结果写入 `preference_summary.summary_json` 的 `dimensions` 字段，语言模型据此生成画像文字并写入 `narrative` 字段。维度由统计产生，文字由模型改写，两者来源分离。

每个维度项带 `reason` 字段，记录该结论的来源规则，例如 theme 的"从行程偏好标签中统计高频主题"。该字段随画像和偏好召回一并返回，用于向用户解释偏好是如何得出的。维度值取不到时（如行程没有预算字段）该条样本跳过，不生成空结论。

历史行程少于 3 条时不生成画像，`eligible` 置为 false。数据库约束 `ck_summary_eligible` 限定 `eligible=TRUE` 时 `sample_count>=3`，业务层按同一规则返回空画像，保证样本量不足时不输出结论。

### 偏好记忆库

每条偏好对应一条 `user_preference` 记录，包含偏好键、值、来源、置信度、权重与最后使用时间。从历史中观测到新证据时写入 `preference_evidence`，以 `evidence_hash` 去重。偏好权重随时间衰减，长期未使用的条目影响逐步降低。

后续生成行程时，按权重与时效召回 TOP-K 条偏好，作为软约束注入智能体上下文。若用户在本次输入中明确指定了城市、预算或景点，则以显式输入为准，历史偏好不覆盖。该边界用于保证用户当下的需求优先于历史推断。

## 数据表

S04 已冻结，S24 沿用以下四张表：

- `trip`、`trip_version`：历史行程及其版本
- `user_preference`：偏好条目，按 `version_no` 追加版本，清空时写 `status=CLEARED`，不执行物理删除
- `preference_evidence`：偏好证据，以 `evidence_hash` 去重
- `preference_summary`：画像快照，按 `summary_version` 追加版本

## 反幻觉设计

| 数据              | 产生方式             | 语言模型是否参与 |
| --------------- | ---------------- | -------- |
| 统计维度 dimensions | SQL 规则聚合         | 否        |
| 画像文字 narrative  | 依据 dimensions 改写 | 是        |
| 偏好权重与置信度        | 规则计算             | 否        |

语言模型只接收已完成统计的结果，不接触原始数据，无法生成数值。画像文字与统计维度分开存储，便于核验文字表述与统计结果是否一致。

## 接口

接口按 OpenAPI 3.1 与 RESTful 规范设计，定义见 `contracts/openapi/s24-preference.yaml`。

| 方法     | 路径                          | 用途       |
| ------ | --------------------------- | -------- |
| GET    | /api/v1/history/trips                   | 查询历史行程列表 |
| POST   | /api/v1/trips/{id}/reuse                | 再来一单     |
| GET    | /api/v1/trips/{id}/versions/compare     | 版本演进对比   |
| GET    | /api/v1/preferences/summary             | 读取偏好画像   |
| DELETE | /api/v1/preferences/summary             | 一键清空画像   |

两个写操作在 Header 中接收 `Idempotency-Key`，取值为 1 至 128 位字母数字及 `._:-`，校验后做 SHA-256 哈希。reuse 以用户标识与哈希值构成去重键，5 分钟内相同键的重复提交直接返回首次结果，避免重复创建草稿；Service 方法使用 synchronized 防止并发写入冲突。

去重记录保存在服务进程内存，服务重启后清空。单机部署下该方案满足需求。多实例部署时需要改用数据库唯一键，并新增对应的 Flyway 迁移。
