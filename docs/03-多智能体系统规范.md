# 行程规划多 Agent 系统规范

> 本文档定义 7 个 Agent 的**职责划分**、**数据源边界**、**失败降级策略**与**公共消息封套**。
> 每个 Agent 的接口契约（输入/输出 JSON Schema）与提示词模板分别存放在 `agents/<编号>-<名称>/` 下。

---

## 1. 系统概览

一条主线：**总控对外，6 个专业 Agent 对内**。总控是唯一与用户对话的 Agent，拥有最终裁决权；其余 6 个只对总控负责，各自从指定数据源取数。

```
用户
 │  (唯一对话)
 ▼
┌─────────────────────┐
│ 01 总控调度 Agent     │  ← 理解需求 / 拆任务 / 调度 / 整合 / 冲突消解 / 最终裁决
└─────────┬───────────┘
          │ 调度子 Agent（消息封套）
  ┌───────┼───────────────┬───────────────┬───────────────┬───────────────┐
  ▼       ▼               ▼               ▼               ▼               ▼
02 路线   03 气象服务     04 景点资讯      05 餐饮住宿      06 预约规则      07 交互修正
规划     (天气API)      (本地知识库)     (POI检索)      (人工规则库)    (当前行程+知识库)
```

| 编号 | Agent | 对外/对内 | 数据源 | 输出 |
|---|---|---|---|---|
| 01 | 总控调度 | **对外** | 子 Agent 结果 | 最终行程方案 |
| 02 | 路线规划 | 对内 | 地图 API | 排序点位序列、逐段路线 |
| 03 | 气象服务 | 对内 | 天气 API | 逐日天气、出行建议、备选方案 |
| 04 | 景点资讯 | 对内 | 本地知识库 | 景点资讯卡 |
| 05 | 餐饮住宿 | 对内 | POI 检索 | 每餐候选、住宿建议 |
| 06 | 预约规则 | 对内 | 人工规则库 | 预约信息卡、预约时间线 |
| 07 | 交互修正 | 对内 | 当前行程 + 知识库 | 影响范围、最小改动方案、变更摘要 |

---

## 2. 划分原则（五条划分线）

| 维度 | 划分线 |
|---|---|
| 对外/对内 | 只有总控对外，其他 6 个对内 |
| 事实数据 | 每个 Agent 只从自己指定的数据源取数，**不跨源** |
| 能不能编 | 所有 Agent **都不能编造事实数据**，查不到就说查不到 |
| 失败降级 | 每个 Agent 都有明确降级策略，**不阻塞整体** |
| 修改范围 | 交互修正 Agent 只做最小改动，**不全量重生成** |

---

## 3. 数据来源与编造边界

| Agent | 数据来源 | 不能编造 |
|---|---|---|
| 总控调度 | 子 Agent 结果 | 不能生成事实数据（时长/票价/政策） |
| 路线规划 | 地图 API | 不能编造通勤时长 |
| 气象服务 | 天气 API | 不能编造天气 |
| 景点资讯 | 本地知识库 | 不能编造资讯 |
| 餐饮住宿 | POI 检索 | 不能编造店名 |
| 预约规则 | 人工规则库 | 不能编造政策 |
| 交互修正 | 当前行程 + 知识库 | 不能编造改动 |

---

## 4. 失败降级策略

| Agent | 失败时怎么办 |
|---|---|
| 总控调度 | 标 `partial`，用 `degraded_fields` 列出缺失/降级字段 |
| 路线规划 | 读缓存 → 直线距离估算，标 `is_estimated` |
| 气象服务 | 标「天气服务暂不可用」 |
| 景点资讯 | 返回空卡片，标 `source=unknown` |
| 餐饮住宿 | 说「附近暂无推荐」 |
| 预约规则 | 说「暂未收录预约信息」 |
| 交互修正 | 说「无法定位修改范围」，请用户澄清 |

降级原则：**单个子 Agent 降级不阻塞整体**，总控用 `degraded_fields` 汇总后继续产出可交付的方案。

---

## 5. 公共消息封套（Envelope）

所有对内 Agent 的输出统一套用以下封套，总控据此判断是否降级：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `schema_version` | string | 是 | 契约版本，由服务封装层注入 |
| `task_id` / `trace_id` / `request_id` | string | 是 | 任务、链路和请求标识，由服务端注入 |
| `generated_at` | date-time | 是 | 服务输出生成时间，由服务端注入 |
| `status` | enum | 是 | `ok`=完整成功 / `partial`=部分子项缺失 / `degraded`=触发降级 / `failed`=失败 |
| `message` | string | 条件必填 | partial/degraded/failed 时必填的人类可读说明 |
| `error_code` | string | 条件必填 | failed 时必填的稳定机器错误码 |
| `degraded_fields` | string[] | 条件必填 | partial/degraded 时必须为非空数组 |

封套内联在每个 Agent 的 `output.schema.json` 顶层，Agent 专属载荷与封套并列。模型只生成状态和专属载荷；服务端注入系统字段后执行最终 Schema 校验。`failed` 不得被迫生成成功载荷。

---

## 6. 消息流（典型一次请求）

1. 总控接收用户完整需求，抽取城市/日期/偏好。
2. 总控并行/串行调度：路线规划、气象服务、景点资讯、餐饮住宿、预约规则。
3. 各子 Agent 返回带封套的结果；降级者由总控记录到 `degraded_fields`。
4. 总控整合为最终 `plan`，冲突时以总控裁决为准。
5. 用户提出修改 → 交互修正 Agent 定位影响范围 → 最小改动 → 版本 +1 → 波及必去景点先问用户。
