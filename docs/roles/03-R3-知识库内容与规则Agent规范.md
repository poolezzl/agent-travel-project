# 03 R3 知识库、内容与规则 Agent 规范

## 1. 责任边界

R3 主责景点资讯 Agent、知识库/RAG、餐饮住宿 Agent、预约规则 Agent 和相应运营工具。数据来源仅限人工运营、官方公开资料、获得许可的 UGC 与合法 POI；严格禁止内容平台爬虫、未许可批量抓取和用 LLM 补造事实。

## 2. 景点知识库与 RAG

- 景点以内部 ID 为主键，建别名、城市、坐标、行政区和合并历史；同名实体由运营人员确认，不能由 embedding 自动合并。
- 每个知识条目保存来源 URL/许可、录入/审核人、发布日期、核验时间、有效期、版本、审核状态和 chunk ID。开放时间、玩法、建议时长、无障碍等事实要单独字段并带来源。
- 召回仅检索已发布、未下架且符合城市/时间的内容；返回引用 chunk/source，低置信度要降级为未知。RAG 生成只能摘录/归纳已召回内容，不能扩展到未提供事实。

## 3. 餐饮住宿 Agent

- 只消费 POI 适配器给出的 POI ID、名称、坐标、类别、数据时间和许可范围；候选与当前行程的“顺路性”须以路线计算或明确估算依据表示。
- 价格必须标人均/每晚、币种、数据时间和精确值/区间/未知；不能从点评文案推算价格。忌口、宗教、儿童等偏好为敏感上下文，只传最小必要字段且不用于公共画像。
- POI 空、过期或失败时返回空候选和降级状态，不临时编店名；外链先通过安全白名单与跳转审计。

## 4. 预约规则与运营

- 规则版本至少包含景点 ID、票种/适用人群、预约要求、渠道、放票时间及其时区、提前天数、票价、免票条件、闭馆/节假日例外、生效期、最后核验、来源和审核状态。
- 超过 30 天未核验默认 `stale`；对外明确“请以官方渠道为准”。计算提醒时处理放票跨月、非工作日、时区和过期规则，避免产生已错过或不存在的提醒。
- 后台编辑采用草稿→复核→发布→停用/回滚；发布、批量导入、合并实体和人工纠错均审计。历史行程引用来源快照，不能因规则更新而失去可解释性。

## 5. 测试与禁止事项

测试必须包含同名景点、别名、空检索、过期内容、错误来源、RAG 幻觉、POI 缺价/缺坐标、规则冲突、过期预约、恶意 UGC 文本与并发发布。禁止：将用户 UGC 未审查直接写入知识库、用模型生成预约政策、仅凭景点名称关联政策、删除被历史版本引用的来源记录。交付每个 Agent 的 Schema 样例、来源回查、降级演示与运营审核流程。

## 6. 逐步开发提示词

### R3-00 数据字典与来源台账

```text
请建立 docs/data/knowledge-data-dictionary.md、source_registry、attraction/poi/reservation 的导入模板和脱敏样例。
为每个事实字段定义来源、许可、录入人、核验时间、有效期、审核状态、版本和历史引用策略；列出禁止来源（未授权爬取、无法证明许可的图片、模型生成政策）。暂不发布生产数据。
```

### R3-01 景点实体与知识库导入

```text
实现景点内部 ID、别名、城市/坐标、合并拆分审计、批量导入预览、错误清单和草稿→复核→发布流程。
导入不依赖名称唯一匹配；同名/坐标冲突进人工队列。RAG 只召回 published 且未过期条目，并返回 chunk/source 引用。测试空召回、低置信度、下架和历史快照。
```

### R3-02 景点资讯 Agent

```text
基于已发布知识库实现景点资讯 Agent。输出玩法、建议时长、避坑、热度时必须关联 source/chunk/retrieved_at；无记录返回 source=unknown，不允许 LLM 补写。
用同名景点、过期条目、冲突条目、恶意文本和模型越界案例测试 Schema 与降级。
```

### R3-03 预约规则库与 Agent

```text
实现预约规则版本、适用日期/人群、渠道、放票时区、提前天数、票价币种、免票条件、最后核验、stale 判定和提醒时间线。
规则必须草稿→复核→发布→停用/回滚，超过 30 天显示待官方核验。测试跨月放票、过期、节假日例外、票价缺失和重复规则；严禁模型生成政策。
```

### R3-04 餐饮住宿 Agent 与运营验收

```text
只使用合法 POI ID/位置/价格数据，按顺路性和同行人偏好返回候选；缺价返回区间/未知，不编店名。
接入 R2 路线结果验证 detour_min，完成四个 Agent 的契约、来源回查、权限、审计和降级测试，并提交首发城市数据质量报告。
```
