# 00 公共工程与协作规范

## 1. 固定边界与技术基线

- 技术栈：Java 21/Spring Boot 3.x/Maven，Python 3.11+/FastAPI/LangGraph/Pydantic v2，Vue 3/TypeScript/Vite，MySQL 8、Redis、Flyway、Nginx；本地开发可 Compose，交付优先裸机脚本与受限服务账号。
- 本期不做预订支付、真实充值、多人实时协作、行中定位、境外城市和内容平台爬取。TripStar 仅作人工效果基线，不复制 GPL-2.0 代码、Prompt、图片或数据。
- Java 业务服务是 MySQL 唯一写入方；Python Agent 服务只能经 REST/OpenAPI 读写任务上下文与步骤结果，禁止共享库直连或跨服务表查询。
- MySQL 用 InnoDB、utf8mb4、UTC `DATETIME(6)`、小写蛇形命名；金额/积分用 `DECIMAL(18,2)` 或最小单位整数，禁止浮点；所有库变更只经新 Flyway 迁移，禁止改写已发布迁移。

## 2. 四条不可突破红线

1. 路线时长只来自地图；天气只来自天气 API；票价/预约只来自已发布规则库；景点资料只来自本地知识库；餐住名称/位置只来自合法 POI。LLM 不得生成或改写事实值。
2. 每个事实字段应可关联 `source_type`、`source_record_id`/供应商请求摘要、`retrieved_at`、`valid_until`、`freshness_status`、`is_estimated`。无来源、过期、冲突、估算、失败必须可见，不能伪装为确定结果。
3. 已发布行程版本不可原地更新。新版本保存 `parent_version_id`、变更集、来源快照、模型/Prompt/Schema 版本；未影响日期和用户锁定项不可被局部重规划改写。
4. 前端输入的 user/role/balance/price/version/source 统统不可信。所有写操作在后端校验身份、资源归属、状态、乐观锁和幂等键。

## 3. 契约与事件规范

- `agents/` 下的 JSON Schema 是 Agent I/O 权威。先修改 Schema/正反例/消费者契约测试，才修改 Prompt、适配器和编排。破坏性变更使用新版本或并行字段，不静默改语义。
- Agent 服务输出必须含 `schema_version`、`task_id`、`trace_id`、`request_id`、`generated_at` 和 `status`；partial/degraded 必须含非空 `degraded_fields` 和 `message`，failed 必须含稳定 `error_code` 和 `message`。系统字段由网关注入，模型不得生成。
- 所有请求、异步任务、模型调用与审计传递 `request_id`、`trace_id`、`task_id`；创建任务、版本、积分流水、通知和导出另有服务端生成的 `idempotency_key`/业务唯一键。
- 事件只追加并有事件版本。消费者以事件 ID 去重；重试不重复创建版本、扣积分、发送提醒或写互动记录。

## 4. 安全、隐私与日志

- 密钥只经环境变量或受限文件注入；不得提交 `.env`、令牌、真实用户数据、原始 UGC、备份或供应商原始响应。
- 日志禁止 password、authorization、cookie、token、手机号、精确地址、完整私密行程、原始 prompt 和 SQL 参数。模型调用日志只留模型别名、耗时、费用汇总、输入哈希、结果状态和脱敏摘要。
- 富文本、评论、知识库文本、供应商返回均为不可信输入；禁止直接 `v-html`。上传图片校验魔数/MIME/大小/尺寸，剥离 EXIF 定位信息，生成随机对象键和受权访问链接。
- 管理员调整积分、发布规则、下架内容、导出、权限变更和失败退款均写不可修改审计事件；日志查询/导出也审计。

## 5. 通用完成定义

每项工作必须：说明已读资料与 `PENDING`；只做当前范围；列修改文件和兼容影响；运行 lint、单测、契约/迁移/构建等适用检查；测试成功、空值、超时、重复、取消、重启和部分失败；报告风险、回滚和建议提交。不能运行检查时如实说明，不能用 Mock 成功冒充实际能力。

## 6. 协作与提交

- R1 终审 Schema、OpenAPI、状态机与跨模块 ADR；接口消费者必须参与破坏性变更评审。
- 每周以固定脱敏案例评审：硬约束、来源完整率、降级可理解性、局部修改保真、时延和成本。文案美观不能抵消事实错误。
- 提交粒度保持可回滚：`arch:`、`feat(orchestrator):`、`feat(route):`、`feat(wallet):`、`test(eval):`、`security:`、`ops:`。提交说明写需求、测试、数据/API 影响和回滚；合并前执行密钥扫描。

## 8. 统一开发顺序

全局只执行 `docs/04-逐步开发提示词.md` 的 S00-S31。总体顺序为：治理与 ADR → 契约 → 工程骨架 → 数据模型/迁移 → 适配器与 Mock → 业务/Agent → 前端 → 集成测试 → 安全/性能 → 部署。禁止先写 Prompt 或真实业务页面再反向猜接口。
