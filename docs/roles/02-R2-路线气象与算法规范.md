# 02 R2 路线、气象与算法规范

## 1. 责任边界

R2 实现地图/路线调用消费接口、路线规划 Agent、天气 Agent、排序算法和相关测试。第三方 API 的通用鉴权、限流、缓存基础设施由 R5 提供；R2 不直接读取 MySQL、不拼接供应商 Key、不让 LLM 计算路线或天气事实。

## 2. 路线 Agent 规范

- 输入先由 POI 实体消歧为 `poi_id + 坐标 + 城市 + 坐标系`，同名点、跨城市点、缺坐标点必须失败或请求澄清，不能按名称猜测。
- 算法接收确定性点位、必去约束、开放时段、日期、到离时间、交通偏好、最大通勤、同行人限制与时间窗。先实现可解释的贪心+2-opt，复杂需求再引 OR-Tools；随机算法固定 seed 并记录版本。
- 输出逐段起终点 ID、方式、距离、时长、换乘摘要、取得时间、来源与 `is_estimated`；总通勤必须等于逐段汇总。不要把门到门、步行、排队、游玩时长混为路线时长。
- 地图异常：精准匹配缓存→只在明确无缓存时直线估算→显著标 estimated。估算不参与“行程可行”的硬性通过判断；不可达、跨城、超时应回传结构化冲突。

## 3. 天气 Agent 规范

- 查询以城市标准 ID、日期、系统注入的 `today` 和供应商预报窗口为准，使用供应商时区；不得让模型或客户端决定“今天”。
- 每日数据明确 `data_type=预报/气候统计`、取得时间、预报发布时间和来源。超过窗口只能返回气候统计或未知，不能以具体天气、降雨概率或穿衣结论伪装预报。
- 建议仅根据已返回天气和敏感活动规则生成；降水、极端温度、预警、数据缺失均产生可机器识别的建议/风险，不得承诺安全。

## 4. 算法质量门禁

测试覆盖：重复/同名 POI、无坐标、闭馆、跨日、午休、儿童/老人节奏、必去点、不可达、零/负时长、时区夏令边界（即使当前国内城市也不可写死）、地图 429/空数据、缓存参数不一致、预报外日期。对固定输入必须输出稳定排序；每次算法更新跑固定基准并与 TripStar 人工基线比较。

## 5. 禁止事项与验收

禁止直线距离冒充道路路线、LLM 编时长/天气、名称字符串作为唯一主键、缓存跨城市复用、将天气失败写成晴天、吞掉不可行约束。验收需证明每段路线和每日天气均能回查来源与时间，故障降级可见，算法无硬约束违反，并提交单元、契约、Mock 集成和评估集结果。

## 6. 逐步开发提示词

### R2-00 适配器接口与测试夹具

```text
请只创建地图、路径、天气适配器接口、Pydantic/DTO、Mock 响应夹具和错误码，不实现 Agent。
统一超时、供应商别名、请求哈希、取得时间、来源、坐标系、quota/429/timeout/empty 错误；严禁把 Key 写入代码或日志。为成功、空数据、脏 JSON、限流、超时和坐标系错误编写测试。
```

### R2-01 实现 POI 消歧和路线输入校验

```text
实现名称→POI ID 的显式消歧流程；同名、多城市、缺坐标、坐标系不一致和不可达点必须返回结构化澄清/失败。
输入校验开放时间、日期时区、必去点、交通方式、时间窗和同行人限制；不得让 LLM 直接写经纬度或时长。完成后输出契约样例并停止。
```

### R2-02 实现确定性路线算法

```text
先实现可解释的贪心+2-opt 和硬约束检查，记录算法版本与随机种子；暂不接 OR-Tools。
逐日并行计算，输出逐段起终点 ID、方式、距离、duration_min、取得时间、is_estimated 和冲突原因。测试重复点、闭馆、午休、跨日、必去点和无解案例，验证总时长可由分段复算。
```

### R2-03 实现天气窗口与建议

```text
实现预报窗口计算，明确 data_type=预报/气候统计，所有日期按供应商时区处理。
预报外不得生成具体天气结论；敏感活动建议只能引用已返回字段。测试窗口边界、日期倒置、极端天气、空返回和天气服务失败，并保证 degraded_fields 可被总控消费。
```

### R2-04 接入缓存、降级和评估集

```text
接入 R5 缓存适配器，缓存键必须包含城市/坐标/日期/方式/点位/供应商等影响参数。
实现地图缓存→估算降级、天气过期→明确提示；估算不得作为精确事实。用固定 30 案例比较算法版本与 TripStar 人工基线，输出硬约束违反、可行率、P95 时延和来源完整率。
```
